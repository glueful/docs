# Migrations & Schema

Glueful's migration system couples ordered, checksum‑verified files with a fluent, database‑agnostic Schema Builder. It supports extension‑provided migrations, batch rollbacks, seeding patterns, and forward evolution practices that minimize production risk.

> Note: All APIs shown are sourced from existing classes under `src/Database/Migrations/*` and `src/Database/Schema/*`. If signatures change, align examples accordingly.

## When To Use Migrations

| Scenario | Use a Migration | Rationale |
|----------|-----------------|-----------|
| Adding a feature table | Yes | Versioning + deploy reproducibility |
| Hot‑fix small index | Yes (even if urgent) | Maintains audit / rollback path |
| Bulk data correction | Maybe (separate data-only migration) | Enables tracked replay |
| One‑off ad‑hoc query | No | Use direct SQL console; avoid polluting history |

> Tip: Favor idempotent operations inside `up()` (e.g. conditional index create) when teams might replay partially applied branches.

## Migration File Naming & Discovery

Migrations are discovered by scanning a primary directory plus any extension‑registered paths (see `MigrationManager::addMigrationPath()`). Files execute in lexicographic order, so encode chronological order in the filename prefix:

```
YYYYMMDDHHMMSS_Description.php
20250301113045_CreateUsersTable.php
20250301114502_AddIndexesToUsers.php
```

Extension migrations follow the same convention and are merged into the global ordered list before execution. Already‑applied filenames are skipped.

> Warning: Renaming a migration after it is applied breaks checksum lineage. Never rename; add a corrective follow‑up migration instead.

## Version Table Structure

Automatically created (`migrations`) if absent:

| Column | Purpose |
|--------|---------|
| id | Auto increment primary key (execution order within batch) |
| migration | Original filename (unique) |
| batch | Group identifier for rollback sets |
| applied_at | Timestamp of application |
| checksum | SHA‑256 file hash for integrity verification |
| description | Human description from migration class |
| extension | Source extension (null for core) |

> Tip: The checksum lets you detect local divergence (e.g. someone edited a past migration). Prefer creating a new fix migration over editing history.

## Writing a Migration

Each migration implements `MigrationInterface` providing `up()`, `down()`, and `getDescription()`.

```php
use Glueful\Database\Migrations\MigrationInterface;
use Glueful\Database\Schema\Interfaces\SchemaBuilderInterface;

class CreateArticlesTable implements MigrationInterface
{
	public function up(SchemaBuilderInterface $schema): void
	{
		$schema->createTable('articles', function ($table) {
			$table->bigInteger('id')->primary()->autoIncrement();
			$table->string('slug', 150)->unique();
			$table->string('title', 200);
			$table->text('body')->nullable();
			$table->string('author_uuid', 12);
			$table->enum('status', ['draft','published'],'draft');
			$table->timestamp('published_at')->nullable();
			$table->timestamp('created_at')->default('CURRENT_TIMESTAMP');
			$table->timestamp('updated_at')->nullable();

			$table->index('author_uuid');
			$table->index('status');
			$table->index('published_at');
			$table->foreign('author_uuid')->references('uuid')->on('users')->cascadeOnDelete();
		});
	}

	public function down(SchemaBuilderInterface $schema): void
	{
		$schema->dropTableIfExists('articles');
	}

	public function getDescription(): string
	{
		return 'Create articles table with indexing for publication queries';
	}
}
```

> Tip: Keep `down()` symmetrical: every table, index, or column created in `up()` should be removed (where practical) to enable reliable rollbacks in lower environments.

## Executing Migrations

Programmatic usage via `MigrationManager`:

```php
use Glueful\Database\Migrations\MigrationManager;

$manager = new MigrationManager();

// Run all pending
$result = $manager->migrate();
// ['applied' => [...], 'failed' => [...]]

// Run specific file
$manager->migrate('/absolute/path/20250301113045_CreateArticlesTable.php');

// Rollback last N (default 1)
$manager->rollback();
```

Batch number is assigned once per `migrate()` invocation covering all pending files for atomic rollback grouping.

> Warning: Do not mix manual single‐file includes and full `migrate()` runs in the same deploy step; you can create gaps in batch semantics.

## Rollbacks & Batches

Rollback selects recent migrations ordered by batch DESC then id DESC and calls each `down()` in reverse order. Use sparingly in production—prefer forward corrective migrations for already‑deployed changes to avoid data loss.

| Pattern | Guidance |
|---------|----------|
| Feature still in staging | Rollback acceptable |
| Production hotfix mistake | Apply new migration to reverse / adjust |
| Data destructive rollback | Confirm backups & window |

> Tip: Consider disabling rollback commands in production pipelines; require explicit approval or a separate script.

## Extension Migrations

Extensions register their migration directories:

```php
$manager->addMigrationPath(base_path('extensions/aegis/migrations'));
$manager->migrate();
```

The manager tracks which extension each applied migration came from via the `extension` column, enabling targeted audits.

## Schema Builder DSL Overview

Representative column & constraint helpers (see builder interfaces for full list):

| Helper | Effect |
|--------|--------|
| `id()` | Adds primary auto increment (implementation specific) |
| `bigInteger('id')->primary()->autoIncrement()` | Explicit large PK |
| `string('name', 100)` | VARCHAR(100) |
| `text('description')->nullable()` | TEXT NULL |
| `boolean('is_active')->default(false)` | TINYINT(1)/BOOLEAN default |
| `enum('status',[...],'draft')` | Enum with default |
| `json('metadata')->nullable()` | JSON column (native where supported) |
| `timestamp('created_at')->default('CURRENT_TIMESTAMP')` | Creation timestamp |
| `index('status')` | Single column index |
| `unique('slug')` | Unique constraint |
| `foreign('role_uuid')->references('uuid')->on('roles')->cascadeOnDelete()` | FK w/ cascade |

> Note: Use expressive types (enum/json) only when supported by your target engines; fallback strategies may be needed for portability.

### Altering Tables

```php
$schema->alterTable('articles')
	->addColumn('reading_time', ['type' => 'integer', 'nullable' => true])
	->execute();
```

For granular compatibility the interface also exposes backward‑compatible methods (`addColumn`, `dropColumn`, `addIndex`, etc.) mapping to engine‑specific SQL.

### Preview & Validate (Future / Stub)

`preview()` and `validate()` allow dry‑run & linting of pending operations. Once implemented, integrate them into CI to prevent unsafe patterns (dropping non‑empty tables, etc.).

## Data Migrations & Seeding

Seeding (e.g. initial RBAC roles) can live inside a migration (see `SeedDefaultRoles`). Keep pure data seeding separate from structural migrations where the volume is large to avoid locking the schema table for extended periods.

| Approach | Use When | Avoid When |
|----------|----------|-----------|
| Structural + small seed mixed | Few reference rows needed | Large dataset load |
| Separate seed migration | Bulk inserts / enumerations | N/A |
| External ETL script | Millions of rows | You need schema version tracking |

> Tip: For high‑volume seeds, create table + indexes first, then batch insert with minimal logging, then add secondary constraints if needed.

## Integrity & Checksums

Checksum is recorded at apply time. A divergence indicates local mutation of a historical file. Strategy:

1. Detect difference (future CLI: `migrate:verify`).
2. Revert local edit; if change required create a new follow‑up migration.
3. Never force update checksum row manually—breaks chain of custody.

> Warning: Editing applied migration files invalidates assumptions downstream (e.g. later migrations relying on original column defaults).

## Zero‑Downtime Patterns

| Change | Safer Sequence |
|--------|----------------|
| Add NOT NULL column with default | Add nullable column -> backfill -> add NOT NULL + default constraint |
| Rename column | Add new column -> copy data -> update code -> drop old later |
| Drop column | Mark unused (code) -> wait / verify metrics -> drop in later deploy |
| Add index on large table | Create concurrently (Postgres) or during low traffic window (MySQL) |
| Backfill large derived field | Chunked updates outside main transaction |

> Tip: Keep schema transactions small—avoid wrapping multi‑minute backfills; they will lock and block queries.

## Performance & Safety Checklist

| Item | Rationale |
|------|-----------|
| Use chronological filename prefixes | Ensures deterministic execution order |
| Keep migrations focused | Easier review & rollback |
| Avoid editing applied files | Preserves checksum integrity |
| Prefer forward fixes over production rollback | Minimizes data risk |
| Stage large changes behind feature flags | Allows progressive rollout |
| Add indexes that match query predicates | Immediate performance gain |
| Verify foreign key impacts (locking) | Prevents cascading delays |

> Tip: Run `EXPLAIN` on new critical queries in staging after adding indexes to confirm planner improvements.
