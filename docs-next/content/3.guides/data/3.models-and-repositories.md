# Models & Repositories

Repositories provide a thin, intention‑revealing layer over the Query Builder while Models (lightweight data structures or arrays) carry the persisted state. Glueful emphasizes repositories + services rather than heavy active record objects.

> Note: Current code centers on repository classes under `src/Repository/*` (e.g. `BaseRepository`, `UserRepository`, `ResourceRepository`, `UnitOfWork`). Where future richer model abstractions (DTO hydration, validation hooks) are implied they are marked as Future.

## Goals

| Goal | Benefit |
|------|---------|
| Encapsulate persistence | Shields services/controllers from SQL details |
| Standard CRUD patterns | Consistency across entities |
| Bulk operations | Efficient batched writes & deletes |
| Transaction & unit of work support | Atomic multi-entity changes |
| Event dispatch on lifecycle | Observability & side‑effect hooks |

## Repository Anatomy

`BaseRepository` implements core primitives:

| Concern | Implementation Highlight |
|---------|--------------------------|
| Connection reuse | Static shared `Connection` instance |
| Identity | `primaryKey` (defaults to `uuid`) |
| Retrieval | `find`, `findRecordByUuid`, `findWhere`, `findMultiple` (IN batching) |
| Pagination | `paginate(page, perPage, conditions, orderBy)` delegates to Query Builder |
| Lifecycle | `create`, `update`, `delete`, `softDelete`, `bulkCreate`, `bulkUpdate`, `bulkDelete` |
| Events | Dispatches `EntityCreatedEvent` / `EntityUpdatedEvent` (extendable) |
| Bulk efficiency | `insertBatch` under the hood inside optional transaction |

> Tip: Keep repository public APIs minimal—push composition and orchestration logic into dedicated domain services.

### Minimal Concrete Repository

```php
use Glueful\Repository\BaseRepository;

class ArticleRepository extends BaseRepository
{
    public function getTableName(): string { return 'articles'; }

    /** Domain specific query */
    public function findPublished(int $limit = 50): array
    {
        return $this->db->table($this->table)
            ->where(['status' => 'published'])
            ->orderBy(['published_at' => 'DESC'])
            ->limit($limit)
            ->get();
    }
}
```

### Factory Resolution

`RepositoryFactory` centralizes instantiation & caching:

```php
$factory = new RepositoryFactory();
$users = $factory->users();
$generic = $factory->getRepository('any_table');
$notifications = $factory->notifications();
```

> Warning: Avoid constructing repositories directly inside hot loops; reuse factory‑cached instances to prevent unnecessary connection handling.

## Unit of Work

`UnitOfWork` batches new / dirty / removed entity operations and commits all changes within a single transaction:

```php
$uow = new UnitOfWork($factory->getConnection());
$uow->registerNew('articles', ['uuid' => nanoid(), 'title' => 'Draft']);
$uow->registerDirty('articles', $existingUuid, ['title' => 'Revised']);
$uow->registerRemoved('articles', $oldUuid);
$result = $uow->commit(); // atomic
```

| Phase | Action |
|-------|--------|
| Register | Track operations in memory |
| Commit | Begin transaction → apply inserts → updates → deletes → commit |
| Rollback | Clear internal collections (transaction rollback already handled) |

> Tip: Use Unit of Work when a service coordinates multiple repositories or cross‑entity invariants must hold after all operations.

## Lifecycle & Domain Events

`create` and `update` dispatch events (`EntityCreatedEvent`, `EntityUpdatedEvent`) enabling audit logging, projections, cache warming, or asynchronous messaging. Current implementation (as of commit) does not yet emit a deleted event—treat delete/softDelete as silent persistence operations and push any side effects to higher layers.

> Warning: Avoid side effects (emails, external HTTP calls) inside repository methods; defer to event listeners / services to keep persistence fast and deterministic.

## Bulk Operations

`bulkCreate` generates UUIDs & timestamps, wraps a batch insert in an explicit transaction, and returns all assigned identifiers. Use to reduce round trips for imports or seeding flows.

| Method | Use Case |
|--------|---------|
| `bulkCreate` | Initial import, high volume enqueue, seed data |
| `bulkUpdate` | Flag toggles / status changes across many rows |
| `bulkDelete` | Hard cleanup of ephemeral records |
| `bulkSoftDelete` | Retention policy expiration without physical delete |

> Tip: Chunk extremely large batches (e.g. 10k+) to keep memory & transaction lock time bounded.

## Pagination from Repositories

`paginate()` defers to the Query Builder's strategy (offset/keyset). For deep scrolling endpoints prefer keyset pagination directly in repository methods (custom query using `where('id','<', $cursor)` plus `orderBy`).

> Tip: Return a lightweight DTO or array subset instead of `*` for list endpoints—reduces I/O and speeds JSON serialization.

## Soft Deletion Patterns

`softDelete` / `bulkSoftDelete` update a status field rather than removing the row. Complement with a scheduled purge task that permanently deletes rows older than a retention threshold.

| Stage | Step |
|-------|------|
| Mark | `softDelete` sets status or `deleted_at` |
| Grace Period | Background jobs ignore hard delete for X days |
| Purge | Separate job hard deletes & emits deletion events |

> Warning: Ensure all queries filtering active data explicitly exclude deleted states if soft deletes are used (e.g. add global repository condition helper).

## Testing Repositories

| Approach | Benefit |
|----------|--------|
| Use in‑memory SQLite (config override) | Fast isolated tests |
| Wrap each test in transaction + rollback | Clean state without re-migrating |
| Seed only minimal required rows | Faster CI, clearer intent |
| Use factory/helpers to generate data | Consistent test fixtures |

> Tip: Add a lightweight factory helper per aggregate root to reduce duplication in tests.

## Performance & Safety Checklist

| Item | Rationale |
|------|-----------|
| Limit selected columns | Reduce transfer & memory |
| Batch writes with `bulkCreate` | Fewer round trips |
| Use keyset pagination for large lists | Stable latency |
| Keep repository focused | Separation of concerns |
| Wrap cross‑entity operations in UoW | Atomic invariants |
| Emit events after commit only | Prevent ghost side effects |

> Tip: Profile repository heavy paths with query logging enabled to surface N+1 patterns (move repeated lookups into `findMultiple`).

## Data Transfer Objects (DTOs)

While repositories return associative arrays today, you can introduce lightweight DTOs to formalize read/write boundaries without adopting a heavyweight ORM. A DTO is a simple immutable (or minimally mutable) object used for transport across layers.

### Why DTOs?
| Benefit | Explanation |
|---------|-------------|
| Explicit contract | Clarifies which fields a service expects / returns |
| Serialization control | Central place to adjust API shape (e.g. hide internals) |
| Validation seam | Construct DTO only if invariants pass |
| Test clarity | Richer assertions vs generic arrays |

### Example DTO

```php
namespace App\DTO;

final class ArticleDTO
{
    public function __construct(
        public readonly string $uuid,
        public readonly string $title,
        public readonly string $status,
        public readonly ?string $publishedAt,
    ) {}

    public static function fromArray(array $row): self
    {
        return new self(
            uuid: $row['uuid'],
            title: $row['title'],
            status: $row['status'],
            publishedAt: $row['published_at'] ?? null,
        );
    }
}
```

### Repository Returning DTOs

```php
class ArticleRepository extends BaseRepository
{
    public function getTableName(): string { return 'articles'; }

    /** @return ArticleDTO|null */
    public function findDto(string $uuid): ?ArticleDTO
    {
        $row = $this->find($uuid);
        return $row ? ArticleDTO::fromArray($row) : null;
    }

    /** @return ArticleDTO[] */
    public function listPublished(int $limit = 25): array
    {
        $rows = $this->db->table($this->table)
            ->where(['status' => 'published'])
            ->orderBy(['published_at' => 'DESC'])
            ->limit($limit)
            ->get();
        return array_map(fn($r) => ArticleDTO::fromArray($r), $rows);
    }
}
```

> Tip: Keep DTOs slim—no DB access; only pure data + formatting helpers (e.g. `toApi()` method if needed).

### Introducing DTOs Gradually
1. Start with read models for high‑traffic endpoints.
2. Add write (command) DTOs with validation for complex create/update operations.
3. Refactor services to accept DTOs at boundaries (controller ↔ service, service ↔ queue job).

> Warning: Avoid duplicating validation logic—reuse existing validation layer before instantiating DTOs.
