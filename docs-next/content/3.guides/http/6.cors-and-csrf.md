# CORS & CSRF

Manage two distinct concerns: cross‑origin resource sharing (browser security boundary) and cross‑site request forgery (state‑changing request authenticity). They are related but solved with different mechanisms.

## Core Differences

| Aspect | CORS | CSRF |
|--------|------|------|
| Threat | Unauthorized origins reading/modifying data via browser sandbox | Malicious site causing authenticated user to perform unintended action |
| Primary Vector | Browser enforcing origin policy | Implicit cookies / credentials reused automatically |
| Mitigation Mechanism | Response headers (Access-Control-*) & preflight | Synchronizer/Double Submit tokens, SameSite cookies |
| Applies To | Cross-origin requests only | All state-changing (typically non-GET) requests from browsers |
| Server Involvement | Evaluate Origin & method; supply headers | Validate token presence/match; rotate or bound to session |

> Tip: Treat them independently—enabling CORS does not provide CSRF protection.

## CORS Configuration

Typically enforced by `security_headers` middleware. Fine-grained configuration can allow frontend apps (SPA/Native) while blocking unknown origins.

### Configuration (`config/security.php`)

The `cors` and `csrf` arrays inside `config/security.php` centralize environment‑aware defaults:

```php
'cors' => [
	'allowed_origins' => env(
		'CORS_ALLOWED_ORIGINS',
		env('APP_ENV') === 'development' ? '*' : null
	),
	'allowed_methods' => ['GET','POST','PUT','DELETE','OPTIONS'],
	'allowed_headers' => ['Content-Type','Authorization','X-Requested-With'],
	'expose_headers' => ['X-Total-Count','X-Page-Count'],
	'max_age' => 86400,
	'supports_credentials' => true,
],

'csrf' => [
	'enabled' => env('CSRF_PROTECTION_ENABLED', true),
	'tokenLifetime' => env('CSRF_TOKEN_LIFETIME', 3600),
	'useDoubleSubmit' => env('CSRF_DOUBLE_SUBMIT', false),
	'exemptRoutes' => [ /* ... */ ],
],
```

Key points:

| Setting | Purpose | Environment Behavior |
|---------|---------|----------------------|
| `CORS_ALLOWED_ORIGINS` | Whitelisted origins (comma list) or `*` | Defaults to `*` only in development; `null` forces explicit prod config |
| `allowed_methods` | Methods accepted in preflight / actual | Static array; adjust if enabling PATCH/HEAD |
| `supports_credentials` | Enables cookie/auth header sharing | Requires non-wildcard origin in responses |
| `CSRF_PROTECTION_ENABLED` | Toggle CSRF middleware globally | Should remain true outside specialized system-to-system APIs |
| `CSRF_TOKEN_LIFETIME` | Rotational window for issued tokens | Lower for high‑sensitivity apps (e.g. 900s) |
| `CSRF_DOUBLE_SUBMIT` | Enables double submit token pattern | False may imply synchronizer token/session approach |
| `exemptRoutes` | Paths skipped from CSRF enforcement | Includes auth bootstrap & public/webhook endpoints |

### .env Example

```dotenv
# CORS
CORS_ALLOWED_ORIGINS=https://app.example.com,https://admin.example.com

# CSRF
CSRF_PROTECTION_ENABLED=true
CSRF_TOKEN_LIFETIME=3600
CSRF_DOUBLE_SUBMIT=true
```

> Tip: In production never rely on the development wildcard fallback—set `CORS_ALLOWED_ORIGINS` explicitly and audit regularly.

### Allowing Specific Origins

```php
return Response::success(['ok' => true])
	->withCors([
		'https://app.example.com',
		'https://admin.example.com'
	], ['GET','POST','PUT','DELETE'], ['Content-Type','Authorization']);
```

### Preflight (OPTIONS) Requests

Browser sends `OPTIONS /resource` with `Origin` + `Access-Control-Request-Method`.

Server should respond with matching `Access-Control-Allow-*` headers and `200` / `204`. Ensure router or middleware short‑circuits OPTIONS early to avoid unnecessary controller execution.

> Note: Avoid reflecting arbitrary `Origin` headers; explicitly whitelist unless you truly require `*` (public read‑only endpoints).

### Credentials & Cookies

If you must send cookies across origins:

* Set `Access-Control-Allow-Credentials: true`
* Cannot use wildcard `*` for `Access-Control-Allow-Origin`; must echo specific origin
* Configure client `fetch(..., { credentials: 'include' })`

> Warning: Cross‑origin credential flows expand attack surface; prefer token/bearer auth when possible.

## CSRF Protection

CSRF middleware validates a token that cannot be forged by a third‑party site. Common pattern: server issues token (cookie or meta tag) and client echoes via header or body field.

### Double Submit Token Flow (Assumption)

1. User loads page → server sets `XSRF-TOKEN` cookie (httpOnly: false) or returns token in JSON
2. JS reads cookie and sends header `X-CSRF-TOKEN: <value>` on POST/PUT/PATCH/DELETE
3. Middleware compares header value with cookie/session stored value
4. Mismatch → 419/403 error response

Example error payload:

```json
{
	"success": false,
	"message": "CSRF token mismatch",
	"error": { "code": 403, "timestamp": "...", "request_id": "..." }
}
```

### Token Rotation Strategies

| Strategy | Benefit | Trade‑off |
|----------|---------|----------|
| Per session | Simple, low overhead | Longer token lifetime |
| Per request | Strongest replay protection | Higher issuance cost, caching harder |
| Rolling (rotate after N uses) | Balance of security/performance | Slight complexity |

> Tip: Rotate on authentication boundary (login / refresh) to reduce fixation risk without per‑request overhead.

### Safe Methods

Only enforce CSRF on state‑changing methods (POST, PUT, PATCH, DELETE). GET/HEAD should be idempotent and side‑effect free.

> Warning: If a GET endpoint mutates state, browsers cannot protect you—fix the design instead of broadening CSRF scope.

## Integrating Both

Sequence inside middleware stack (recommended):

1. `security_headers` (CORS & base headers)
2. `rate_limit` (prevent abuse before heavy logic)
3. `auth`
4. `csrf` (now you have authenticated context; token may tie to user/session)

> Note: Put CSRF after authentication if tokens are user/session scoped; if global anonymous forms exist, issue a guest token earlier.

## Common Scenarios

| Scenario | CORS Needed? | CSRF Needed? | Notes |
|----------|--------------|--------------|-------|
| Public read‑only API from any origin | Minimal (`*` allow) | No (GET only) | Use caching aggressively |
| SPA + API same apex domain (api.example.com, app.example.com) | Yes (explicit list) | Yes | Consider SameSite=Lax cookies |
| Native mobile app | Usually no (first‑party tokens) | No (tokens not auto-sent by browsers) | Use bearer tokens |
| Third‑party developer platform | Yes (registered origins) | Token or signed requests | Provide management portal |

## Testing Checklist

| Test | Expectation |
|------|-------------|
| OPTIONS preflight with allowed origin | 200 + correct CORS headers |
| OPTIONS with disallowed origin | 403/No CORS headers |
| POST missing CSRF token | 403 / validation error payload |
| POST with mismatched token | 403 with mismatch message |
| Allowed POST with correct token | 2xx success |

## Headers Reference (CORS)

| Header | Purpose |
|--------|---------|
| `Access-Control-Allow-Origin` | Whitelisted origin or `*` |
| `Access-Control-Allow-Methods` | Allowed methods list |
| `Access-Control-Allow-Headers` | Allowed custom headers |
| `Access-Control-Allow-Credentials` | Enable credentialed requests |
| `Access-Control-Max-Age` | Cache preflight (seconds) |
| `Vary: Origin` | Inform caches response varies per origin |

> Tip: Supply a reasonable `Access-Control-Max-Age` (e.g. 600) to reduce preflight chatter while staying responsive to policy changes.

## Common Pitfalls

> Warning: Using `*` with credentials silently fails in browsers—explicit origin required when `Access-Control-Allow-Credentials: true`.

> Tip: Distinguish between “CORS blocked” (browser console) and “403 from server”; debug with network tab + curl reproductions.

> Note: CSRF tokens are not a substitute for authentication; an unauthenticated request with a valid token should still be rejected.
