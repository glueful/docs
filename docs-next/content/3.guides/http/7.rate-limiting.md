# Rate Limiting

Protect capacity, ensure fair usage, and slow abusive patterns by constraining how many requests a client (IP, user, token, key) can perform over a defined sliding window. Rate limiting sits early in the middleware stack—after basic security headers, before expensive auth or business logic when possible.

> Note: Implementation details (middleware alias `rate_limit`) are inferred; adapt names if the final component differs. Patterns below reflect common sliding window / token bucket approaches.

## Core Concepts

| Concept | Description |
|---------|-------------|
| Key | Unique bucket identifier (IP, user_id, API key, composite) |
| Window | Time period (seconds) over which attempts are measured |
| Max Attempts | Total allowed within window |
| Strategy | Algorithm: fixed window, sliding window, token bucket, leaky bucket |
| Penalty | Optional back‑off (e.g. exponential delay) on repeated exhaustion |

## Middleware Usage (Assumption)

Attach via colon parameter syntax: `rate_limit:max,window[,scope]`.

```php
$router->group(['middleware' => ['rate_limit:120,60']], function ($router) {
	$router->get('/search', [SearchController::class, 'index']); // 120 req/min per key
});

$router->post('/auth/login', [AuthController::class, 'login'])
	->middleware('rate_limit:5,60,login'); // 5 per minute for login scope
```

> Tip: Use distinct scopes for different sensitivity levels (login vs general reads) so bursting reads do not starve authentication.

## Choosing a Key

| Context | Key Strategy | Notes |
|---------|--------------|-------|
| Anonymous public API | IP address | Susceptible to NAT aggregation; consider /24 masking awareness |
| Authenticated users | user_id | Combines fairness per account |
| API keys | Provided key string | Good for partner isolation |
| High-risk endpoints | Composite (user_id + path) | Prevent hotspotting on critical routes |
| Mixed (pre-auth) | IP then user swap post-auth | Migrate bucket once identity known |

> Warning: Pure IP limiting is weak behind large corporate NATs—adjust ceilings or add secondary signals (UA hash, ASN heuristics).

## Algorithms Overview

| Algorithm | Pros | Cons | Good For |
|-----------|------|------|----------|
| Fixed window | Simple, low memory | Burst at boundary | Low risk endpoints |
| Sliding window (log or counters) | Smooth, fair | Slightly more compute | General API fairness |
| Token bucket | Allows short bursts | Token math complexity | Latency-sensitive burst tolerance |
| Leaky bucket (queue) | Smooth out spikes | Potential queue latency | Background processing intake |

> Tip: A sliding window counter (two buckets + partial overlap) balances simplicity and burst smoothing for most APIs.

## Data Store

| Store | Latency | Distribution | Notes |
|-------|---------|--------------|-------|
| In-memory (per worker) | Fast | Not shared | Development / single instance only |
| Redis | Low | Cluster ready | Preferred for production horizontal scale |
| Database | Higher | Shared | Avoid; locking and contention risk |

### Adaptive Flags

| Flag | Purpose | When to Enable |
|------|---------|---------------|
| `ENABLE_ADAPTIVE_RATE_LIMITING` | Turns on behavior scoring / dynamic policy adjustments | Production once baseline metrics stable |
| `ENABLE_DISTRIBUTED_RATE_LIMITING` | Enables coordination across nodes (e.g. Redis) | Any multi-instance deployment |
| `ENABLE_ML_RATE_LIMITING` | Experimental ML anomaly scoring | Only after evaluating false positive risk |

### Timing Parameters

| Setting | Meaning | Tuning Guidance |
|---------|---------|-----------------|
| `sync_interval` | Seconds between adaptive state syncs | Shorter = fresher signals, higher overhead |
| `rule_update_interval` | How often adaptive rules recalc | Increase if rules stable to reduce churn |
| `behavior_ttl` | Lifetime of behavior score cache | Long enough to capture sustained patterns |
| `anomaly_ttl` | Duration anomaly markers persist | Keep > typical attack window for correlation |

## Headers

Return standardized headers to inform clients of quota state (names may differ; align with final implementation):

| Header | Meaning |
|--------|---------|
| `X-RateLimit-Limit` | Total allowed in current window |
| `X-RateLimit-Remaining` | Attempts left before 429 |
| `X-RateLimit-Reset` | Epoch seconds when window resets (or tokens refill) |
| `Retry-After` | Seconds until next allowed request (only on 429) |

> Note: `Retry-After` is mandatory for well-behaved clients performing backoff.

## Progressive Policies

| Endpoint | Policy | Rationale |
|----------|--------|-----------|
| POST /auth/login | 5 per 60s | Brute force deterrence |
| POST /auth/verify-otp | 3 per 300s | Slows multi-factor brute attempts |
| GET /search | 120 per 60s | Reasonable interactive use |
| POST /payments | 10 per 300s | Prevent replay and abuse |
| POST /support/tickets | 20 per 3600s | Spam control |

> Tip: Document policies publicly so integrators can design resilient backoff.

## Sliding Window (Two-Bucket) Logic (Illustrative)

```php
function remaining(string $key, int $max, int $window, Redis $r): int {
	$now = time();
	$currentBucket = intdiv($now, $window);
	$prevBucket = $currentBucket - 1;
	$currentKey = "$key:$currentBucket";
	$prevKey = "$key:$prevBucket";
	$elapsed = $now % $window;
	$weight = ($window - $elapsed) / $window; // proportion of previous bucket still counting
	$current = (int) $r->get($currentKey);
	$previous = (int) $r->get($prevKey);
	$effective = $previous * $weight + $current;
	return max(0, $max - (int) ceil($effective));
}
```

> Warning: Use LUA scripts / transactions to increment and read atomically in production for correctness under concurrency.

## Ordering in Middleware Stack

1. `security_headers`
2. `rate_limit`
3. `auth`
4. `csrf`
5. `permissions`
6. Business / shaping middleware

Early placement ensures abusive traffic is rejected before hitting authentication backends.

## Observability

Emit structured events on each 429 containing: key, scope, remaining=0, window, request_id, route. Aggregate to detect systemic attacks vs organic bursts.

> Tip: Alert on sudden increase in unique limiter keys exceeding 50% of typical baseline—may indicate distributed probing.

## Tuning & Performance

| Technique | Benefit | Notes |
|-----------|---------|-------|
| Sliding window counters | Smooth boundaries | Two counters + math; low memory |
| Pre-hash keys | Uniform distribution | Avoids hot key imbalance |
| Coalesce increments | Fewer network round trips | Batch via pipeline when possible |
| Distinguish scopes | Prevents one route starving others | Separate buckets |
| Soft warnings | Let clients know at <10% remaining | Optional header/field |

## Common Pitfalls

> Warning: Not setting `Retry-After` deprives clients of proper backoff guidance—expect aggressive retries.

> Tip: Keep limits generous enough to avoid harming typical UX; rely on anomaly detection for sophisticated abuse.

> Note: Always log the effective key to correlate incidents (avoid hashing without reversible mapping internally).
