# Notifications

Notifications deliver user or system facing messages across channels (email today; extensible to push, SMS, in‑app, webhook). The `email-notification` extension provides templating, rate limiting, queuing, retries, monitoring hooks, and basic analytics toggles.

## Installation

If you used the API skeleton this extension may already be present. Otherwise:

```bash
composer require glueful/extensions-email-notification
```

Then ensure it is registered (auto-discovery or explicit) in your `config/extensions.php` (or equivalent). The service provider is:

`Glueful\\Extensions\\EmailNotification\\EmailNotificationServiceProvider`

On boot it:

1. Merges `email-notification` config defaults.
2. Registers `EmailFormatter`, `EmailNotificationProvider`, and `EmailChannel` services.
3. Registers the `EmailChannel` with the framework `ChannelManager`.
4. Registers its internal event listener for notification lifecycle events.

## Configuration Snapshot
`extensions/email-notification/config/email-notification.php`:
```php
return [
  'templates' => [
    'extension_path' => __DIR__.'/../src/Templates/html',
    'extension_mappings' => [ 'verification' => 'verification', 'password-reset' => 'password-reset', 'welcome' => 'welcome', 'alert' => 'alert', 'default' => 'default'],
    'processing' => [
      'minify_html' => env('MAIL_MINIFY_HTML', false),
      'inline_css' => env('MAIL_INLINE_CSS', true),
      'auto_text_version' => true,
    ],
  ],
  'rate_limit' => [
    'enabled' => env('MAIL_RATE_LIMIT_ENABLED', true),
    'max_per_minute' => env('MAIL_RATE_LIMIT_PER_MINUTE', 10),
  ],
  'queue' => [
    'enabled' => env('MAIL_QUEUE_ENABLED', true),
    'queue_name' => env('MAIL_QUEUE_NAME', 'emails'),
    'max_attempts' => env('MAIL_QUEUE_MAX_ATTEMPTS', 3),
  ],
  'events' => [
    'enabled' => env('MAIL_EVENTS_ENABLED', true),
    'fire_events' => [ 'email.sending' => true, 'email.sent' => true, 'email.failed' => true ],
  ],
  'retry' => [
    'enabled' => env('MAIL_RETRY_ENABLED', true),
    'delay' => env('MAIL_RETRY_DELAY', 300),
    'backoff' => env('MAIL_RETRY_BACKOFF', 'exponential'),
  ],
  'monitoring' => [
    'enabled' => env('MAIL_MONITORING_ENABLED', true),
    'track_opens' => env('MAIL_TRACK_OPENS', false),
  ],
];
```

## Core Concepts
| Concept | Summary | Benefit |
|---------|---------|---------|
| Template Mapping | Key → HTML/markdown asset | Consistent brand & layout |
| Rate Limiting | Env-configured quotas per minute/hour/day | Abuse & cost control |
| Queue Offload | Async send via queue driver | Fast responses |
| Retry Strategy | Controlled reattempts with backoff | Resilience to transient SMTP/API faults |
| Events | Emits lifecycle + channel events | Observability & chaining |
| Analytics | Optional opens/clicks tracking | Engagement insight |
| Channel Manager | Registry of available channels | Pluggable multi-channel delivery |

## Sending an Email (Concrete Example)
```php
use Glueful\Extensions\EmailNotification\EmailChannel;
use Glueful\Extensions\EmailNotification\DummyNotifiable;

/** @var EmailChannel $email */
$email = app(EmailChannel::class);

$email->send(
  notifiable: new DummyNotifiable('user@example.com'),
  template: 'welcome',
  data: [
    'name' => 'Jane',
    'cta_url' => 'https://app.example.com/activate'
  ],
  options: [
    'subject' => 'Welcome to Glueful!',
    'tags' => ['onboarding']
  ]
);
```
If queueing is enabled the call enqueues a job; otherwise it sends inline.

> Tip: Always include a stable semantic `tags` array for downstream analytics & suppression logic.

> See also: End-to-end batching and campaign orchestration in the tutorial [Background Jobs + Notifications](/tutorials/jobs-notifications#step-3-create-background-jobs).

## Rate Limiting
Configured thresholds (`MAIL_RATE_LIMIT_*`) prevent burst abuse. Exceeding limits should raise a specific exception—catch and degrade (e.g., schedule later) rather than hiding.

## Retry & Backoff
Exponential backoff with jitter reduces retry storms against degraded providers. Keep `max_attempts` low for non-critical transactional messages; prefer escalation to a fallback channel for persistent failures.

## Template Processing
Inlining CSS and generating a text alternative improves deliverability and accessibility. Minify HTML in production only—avoid confusing diff-based template reviews.

::: tip
Centralize all dynamic URLs in template data arrays so you can sign or version them consistently.
:::

::: warning
Do not embed secrets or raw tokens directly in templates—always use time-bounded, signed URLs.
:::

## Events Integration & Lifecycle
The notification system emits a rich set of lifecycle events (via concrete classes) enabling instrumentation and cross-extension fan‑out. See the full catalog in the [Events & Listeners guide](/guides/core-services/events-and-listeners#built-in-events--core-listeners).

| Phase | Event Class | Trigger | Common Uses |
|-------|-------------|---------|-------------|
| Queued | `NotificationQueued` | Notification accepted and queued | Throughput metrics |
| Scheduled | `NotificationScheduled` | Future timestamp schedule persisted | Reminder dashboards |
| Dispatch Start | `NotificationSent` | Channel hand-off begins | Start latency timer |
| Retry | `NotificationRetry` | Retry attempt (backoff) | Retry exhaustion alerting |
| Delivered | `NotificationDelivered` | Provider confirms send | Success KPI, engagement fan‑out |
| Failed | `NotificationFailed` | All retries exhausted | Dead-letter / fallback channel |
| Read | `NotificationRead` | User opened / interacted | Engagement analytics |

Legacy string events (`email.sending`, `email.sent`, `email.failed`) may also be fired if enabled for backward compatibility—prefer class based listeners.

> Warning: Avoid heavy synchronous logic in these listeners—offload to jobs. Slow handlers degrade system-wide dispatch throughput.

## Monitoring
Track send latency, failure rate, retry distribution, rate limit rejections. Sudden latency spike often indicates upstream throttling or DNS/connect issues.

Cross-reference: Queue worker monitoring patterns in [Background Jobs + Notifications](/tutorials/jobs-notifications#step-10-monitoring-and-metrics).

| Symptom | Cause | Action |
|---------|-------|--------|
| Missing variables in template | Data array key mismatch | Align keys, add template validation test |

## Extending to Other Channels (Push, SMS, In‑App)

To add a new channel:

1. Create an extension with a service provider.
2. Implement a channel class (mirroring `EmailChannel::send()` signature conceptually).
3. Register it with the `ChannelManager` in your provider's `boot()` method.
4. (Optional) Provide templates / formatting abstraction similar to `EmailFormatter`.
5. Listen to notification lifecycle events to enrich telemetry or invoke channel-specific optimizations.

Patterns:
| Pattern | Why |
|---------|-----|
| Queue all outbound sends | Keeps request latency low |
| Use idempotent send logic | Prevent duplicates on retries |
| Emit only necessary extra events | Reduce noise, leverage core lifecycle |
| Centralize rate limits per channel | Coordinated throttling and fairness |

> Tip: Start by modeling push or SMS as another channel before designing user preference matrices—early over-abstraction slows iteration.
