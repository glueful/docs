# Notifications

Notifications deliver user or system facing messages across channels (email today; extensible to push, SMS, in‑app, webhook). The `email-notification` extension currently provides templating, formatting and retry plumbing. Configuration keys for rate limiting, queue offload, legacy string events, open/click analytics, and bounce handling are present but (as of this version) are placeholders with no enforcement or emission logic. Where features are aspirational / planned they are explicitly marked below.

## Installation

If you used the API skeleton this extension may already be present. Otherwise:

```bash
composer require glueful/extensions-email-notification
```

Then ensure it is registered (auto-discovery or explicit) in your `config/extensions.php` (or equivalent). The service provider is:

`Glueful\\Extensions\\EmailNotification\\EmailNotificationServiceProvider`

On boot it:

1. Merges `email-notification` config defaults.
2. Registers `EmailFormatter`, `EmailNotificationProvider`, and `EmailChannel` services.
3. Registers the `EmailChannel` with the framework `ChannelManager`.
4. Registers its internal event listener for notification lifecycle events.

## Core Concepts
| Concept | Summary | Benefit |
|---------|---------|---------|
| Template Mapping | Key → HTML/markdown asset | Consistent brand & layout |
| Rate Limiting | Env-configured quotas per minute/hour/day | Abuse & cost control |
| Queue Offload | Async send via queue driver | Fast responses |
| Retry Strategy | Controlled reattempts with backoff | Resilience to transient SMTP/API faults |
| Events | Emits lifecycle + channel events | Observability & chaining |
| Analytics | Optional opens/clicks tracking | Engagement insight |
| Channel Manager | Registry of available channels | Pluggable multi-channel delivery |

## Sending an Email (Concrete Example)
Preferred high‑level API: `NotificationService` (persists + dispatches) rather than calling the channel directly.

```php
use Glueful\Notifications\Services\NotificationService;
use Glueful\Extensions\EmailNotification\DummyNotifiable; // Example notifiable implementing Notifiable

/** @var NotificationService $notifications */
$notifications = app(NotificationService::class);

$notifiable = new DummyNotifiable('user@example.com');

$result = $notifications->send(
    type: 'user.welcome',
    notifiable: $notifiable,
    subject: 'Welcome to Glueful!',
    data: [
        // Channel formatters will consume these keys.
        'template' => 'welcome',        // Consumed by EmailFormatter / EnhancedEmailFormatter
        'name' => 'Jane',
        'cta_url' => 'https://app.example.com/activate'
    ],
    options: [
        // Optional: restrict to explicit channels (defaults: user preference -> config -> all available)
        'channels' => ['email'],
        // Optional scheduling (DateTime instance) => returns ['status' => 'scheduled', ...]
        // 'schedule' => (new DateTime('+10 minutes')),
        'priority' => 'normal'
    ]
);

// $result example (single channel success):
// [
//   'status' => 'success',
//   'sent_count' => 1,
//   'total_channels' => 1,
//   'channels' => [ 'email' => ['status' => 'success'] ]
// ]
```

Direct channel usage is lower‑level and expects already formatted data (e.g. `html_content` / `text_content`). Use only if bypassing persistence.

> Tip: Provide a `template` key plus raw variables; the email formatter adds `html_content`/`text_content` automatically when needed.

> Note: Queue, rate limit, and analytics configs are placeholders—sending is currently synchronous in the dispatcher path.

> See also: End-to-end batching and campaign orchestration in the tutorial [Background Jobs + Notifications](/tutorials/jobs-notifications#step-3-create-background-jobs).

## Rate Limiting
Placeholder: Configuration keys (`MAIL_RATE_LIMIT_*`) exist but no enforcement logic currently runs inside `EmailChannel` or the dispatcher. If you need limits now, wrap calls to `NotificationService::send()` with your own rate limiter service and/or implement a custom notification extension.

## Retry & Backoff
Implemented: Failures emit `notification.failed` and the email listener delegates to `NotificationRetryService`.

Supported strategies (config `retry.backoff`):
- `exponential` (default): delay * 2^(attempt-1)
- `linear`: delay * attempt
- Any other value: fixed delay

Delay base: `retry.delay` (seconds). Retry count persisted in notification `data.retry_count`. Retries are scheduled in `notification_retry_queue` with a per‑row `retry_at` timestamp.

Partial success semantics: If multiple channels are attempted, the notification is marked sent if at least one succeeds; failed channels may still queue retries.

## Template Processing
Inlining CSS and generating a text alternative improves deliverability and accessibility. Minify HTML in production only—avoid confusing diff-based template reviews.

::: tip
Centralize all dynamic URLs in template data arrays so you can sign or version them consistently.
:::

::: warning
Do not embed secrets or raw tokens directly in templates—always use time-bounded, signed URLs.
:::

## Events Integration & Lifecycle
Current (implemented) emission is intentionally minimal. Only two concrete events are fired today by the dispatcher path:

| Event Class | When Fired | Notes / Uses |
|-------------|------------|--------------|
| `NotificationSent` | After a channel send completes successfully | Use for success metrics, latency measurement (measure start externally). |
| `NotificationFailed` | After a channel send attempt fails (and before scheduling a retry) OR after final exhaustion | Drive retry/backoff metrics & alerting. |

Scheduling does NOT currently emit a dedicated event. A call to `NotificationService::send()` with a future schedule returns a result array containing `['status' => 'scheduled']` and defers actual sending until the scheduler triggers dispatch. No `NotificationScheduled` event is emitted yet.

Planned / not yet implemented events (subject to change):
- Queued (`NotificationQueued`)
- Scheduled (`NotificationScheduled`)
- Retry (`NotificationRetry`) – may wrap existing internal retry scheduling
- Delivered (`NotificationDelivered`) – would require provider webhook or success callback enrichment
- Read / Open (`NotificationRead`) – would require tracking pixel / click instrumentation

Legacy string events (`email.sending`, `email.sent`, `email.failed`) are present only as config placeholders; they are NOT emitted in this version. Prefer class-based events once they exist; avoid depending on the legacy keys.

> Warning: Avoid heavy synchronous logic in listeners—offload to jobs. Slow handlers degrade system-wide dispatch throughput.

### Channel Resolution Order
How the framework decides which channels to attempt for a `NotificationService::send()` call:
1. Explicit `options['channels']` if provided.
2. Notifiable user preferences (e.g. stored channel enables/disabled) – if implemented in your app layer.
3. Global notification configuration defaults.
4. Fallback: all registered channels (currently just `email`).

### Extension Hook Pipeline (Email)
The email extension may expose formatter steps that transform provided `data` into `html_content` / `text_content`. Conceptually:
1. Gather base data (`template`, variables).
2. Formatter resolves template mapping and renders HTML.
3. CSS inlining + optional HTML minify.
4. Auto-generate text alternative (if enabled).
5. Channel sends using resulting payload.
Downstream listeners (retry, metrics) observe `NotificationSent` / `NotificationFailed` only.

### Partial Success & Idempotence
If multiple channels are attempted in the future, a notification is considered overall successful once at least one channel succeeds; failed channels can still schedule retries. The system should (design intent) skip re-sending a channel if it has already been marked successful to prevent duplicates (idempotence). Current single-channel implementation makes this largely implicit.

### Scheduling Semantics
- Immediate send (no schedule) returns a result with `status: success` or `status: failure`.
- Future schedule returns `status: scheduled`; no event is emitted until actual dispatch time.
- A dispatcher encountering a notification whose `scheduled_at` is still in the future should return a `deferred`/no-op result (implementation specific) without emitting events.

### Planned Features / Placeholders
The following configuration keys exist but have no active logic yet:
- Rate limiting (`rate_limit.*`)
- Queue offload (`queue.*`) – sending is synchronous in-process
- Additional lifecycle events (Queued, Scheduled, Retry, Delivered, Read)
- Legacy string events emission (`events.fire_events` map)
- Monitoring: opens / read tracking (`monitoring.track_opens`) – no pixel/click implementation

These are marked to avoid accidental reliance; treat them as forward-looking scaffolding.

## Extending to Other Channels (Push, SMS, In‑App)

To add a new channel:

1. Create an extension with a service provider.
2. Implement a channel class (mirroring `EmailChannel::send()` signature conceptually).
3. Register it with the `ChannelManager` in your provider's `boot()` method.
4. (Optional) Provide templates / formatting abstraction similar to `EmailFormatter`.
5. Listen to notification lifecycle events to enrich telemetry or invoke channel-specific optimizations.

Patterns:
| Pattern | Why |
|---------|-----|
| Queue all outbound sends | Keeps request latency low |
| Use idempotent send logic | Prevent duplicates on retries |
| Emit only necessary extra events | Reduce noise, leverage core lifecycle |
| Centralize rate limits per channel | Coordinated throttling and fairness |

> Tip: Start by modeling push or SMS as another channel before designing user preference matrices—early over-abstraction slows iteration.
