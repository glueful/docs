# Distributed Locks

The distributed locking system prevents duplicate or overlapping execution of critical sections across workers or nodes. It wraps Symfony's Lock component with a simplified `LockManagerInterface` abstraction and pluggable stores (file, Redis, database). Use it to serialize tasks like cache warmers, index rebuilds, inventory adjustments, scheduled job execution, or long‑running imports.

At a glance:
- Simple high‑level helpers: `executeWithLock()` and `waitAndExecute()` wrap acquisition, execution, release.
- Multiple backends: file (default), Redis, database (PDO) via config `lock.php`.
- Per‑resource keys automatically prefixed (default `glueful_lock_`).
- TTL (time‑to‑live) with optional auto‑release semantics prevents permanent deadlocks.
- Non‑blocking and blocking acquisition patterns supported.
- Integrated with `JobScheduler` to guard scheduled job execution (`scheduler:job:<name>` locks).

> Locks ensure **mutual exclusion**, not queueing or durability. For multi-step workflows, combine with **Queues & Jobs** (for retries) and **Transactions** (for atomic DB changes).

## Core Concepts (At a Glance)
| Concept | Artifact | Responsibility | Key Methods / Notes |
|---------|----------|---------------|---------------------|
| Manager | `LockManager` / `LockManagerInterface` | Factory + convenience orchestration | `createLock`, `executeWithLock`, `waitAndExecute`, `isLocked` |
| Lock Object | `LockInterface` | Represents an acquired lock | `acquire()`, `refresh()`, `isExpired()`, `release()` |
| Stores | File / Redis / Database stores | Persist lock state | Configurable in `config/lock.php` |
| Prefix | Configured key prefix | Namespaces lock keys | Default `glueful_lock_` |
| TTL | Lock expiration | Prevents indefinite hold | Pass seconds (float) when creating/executing |
| Conflict Handling | Exceptions + retry loop | Indicate contention | `LockConflictedException` on failure |
| Blocking Wait | `waitAndExecute()` | Poll until free or timeout | Uses maxWait & 100ms sleep |
| Scheduler Integration | `JobScheduler::runJobWithLock` | Avoid overlapping scheduled jobs | Lock key `scheduler:job:<name>` |

## Quick Start
### Execute with Automatic Lock Handling
```php
use Glueful\Lock\LockManagerInterface;

$lockManager = app(LockManagerInterface::class);
$result = $lockManager->executeWithLock('import:daily-customers', function () {
    return (new CustomerImporter())->run();
}, 900); // 15 min TTL
```

### Wait (Block) for a Limited Time
```php
try {
  $data = $lockManager->waitAndExecute('sync:warehouse', function () {
      return runSync();
  }, maxWait: 30.0, ttl: 600);
} catch (\Symfony\Component\Lock\Exception\LockConflictedException $e) {
  // Timed out waiting
  reportBusy('sync:warehouse');
}
```

### Manual Lock Lifecycle
```php
$lock = $lockManager->createLock('rebuild-search-index', ttl: 300);
if ($lock->acquire()) {
  try {
    rebuildIndex();
  } finally {
    $lock->release();
  }
}
```

## Configuration
Location: `framework/config/lock.php`
```php
return [
  'default' => env('LOCK_DRIVER', 'file'),
  'stores' => [
    'file' => [ 'driver' => 'file', 'path' => env('LOCK_FILE_PATH', 'framework/locks'), 'prefix' => 'lock_', 'extension' => '.lock'],
    'redis' => [ 'driver' => 'redis', 'connection' => env('LOCK_REDIS_CONNECTION', 'default'), 'prefix' => env('LOCK_REDIS_PREFIX', 'glueful_lock_')],
    'database' => [ 'driver' => 'database', 'table' => env('LOCK_DB_TABLE', 'locks')],
  ],
  'retry' => [
    'times' => env('LOCK_RETRY_TIMES', 10),
    'delay' => env('LOCK_RETRY_DELAY', 100), // ms between attempts
    'max_wait' => env('LOCK_MAX_WAIT', 10),  // seconds
  ],
];
```

### Environment Variables (Common)
| Var | Purpose |
|-----|---------|
| `LOCK_DRIVER` | Select store: file / redis / database |
| `LOCK_FILE_PATH` | Directory for file locks |
| `LOCK_REDIS_CONNECTION` | Named Redis connection for locks |
| `LOCK_REDIS_PREFIX` | Prefix for Redis keys |
| `LOCK_DB_TABLE` | Table name for database store |
| `LOCK_RETRY_TIMES` | Retry attempts (internal use if implementing loops) |
| `LOCK_RETRY_DELAY` | Milliseconds between retries |
| `LOCK_MAX_WAIT` | Maximum blocking wait (seconds) for high-level operations |

## Usage Patterns
### Idempotent Critical Section
```php
$lockManager->executeWithLock('daily:aggregation', function () {
    AggregateJob::run(); // safe to run once
});
```

### Batch Partition Locks
```php
foreach (array_chunk($userIds, 500) as $chunk) {
  $key = 'recalc:users:' . md5(json_encode($chunk));
  $lockManager->executeWithLock($key, fn() => recalcUserStats($chunk), 300);
}
```

### Conditional Skip if Locked
```php
if ($lockManager->isLocked('cache:warm')) {
  logger()->info('Skipping warm — already in progress');
  return;
}
$lockManager->executeWithLock('cache:warm', fn() => warmCacheLayers(), 600);
```

### Refresh Long Running Lock
```php
$lock = $lockManager->createLock('large:import', ttl: 600);
if ($lock->acquire(true)) { // blocking
  try {
    while (!done()) {
      step();
      if ($lock->getRemainingLifetime() !== null && $lock->getRemainingLifetime() < 120) {
        $lock->refresh(600); // extend
      }
    }
  } finally { $lock->release(); }
}
```

## Error Handling
```php
use Symfony\Component\Lock\Exception\LockConflictedException;
try {
  $lockManager->executeWithLock('inventory:sync', fn() => syncInventory(), 300);
} catch (LockConflictedException $e) {
  // Busy — choose to log or queue retry
  logger()->info('Inventory sync skipped: already running');
} catch (\Throwable $e) {
  logger()->error('Inventory sync failed', ['error' => $e->getMessage()]);
}
```

## Blocking vs Non‑Blocking
- `createLock(...)->acquire()` defaults to non‑blocking (returns false immediately on conflict).
- Pass `acquire(true)` for blocking wait (internally handled by Symfony lock store until acquired or TTL conflict rule).
- Use `waitAndExecute()` for explicit timed polling with `maxWait` semantics and observable wait time logging.

## Choosing a Store
| Store | Strengths | Trade‑offs | Recommended For |
|-------|-----------|-----------|-----------------|
| File | Zero external deps, simple | Single host scope (shared FS required for multi-node), slower on NFS | Local dev, single-server deployments |
| Redis | Fast, atomic, widely supported | Requires Redis infra, TTL accuracy depends on server clock | Production multi-node, high churn locks |
| Database | Leverages existing DB | Higher latency, table contention possible | Low volume locks, minimal infra |

### Prevent Overlapping API Tasks
```php
public function rebuildAnalytics(): Response {
  try {
    $this->lockManager->executeWithLock('analytics:rebuild', fn() => $this->service->rebuild(), 1800);
    return Response::success('Rebuild complete');

    return Response::error('Rebuild already in progress', 409);
  }
}
```

## Monitoring & Observability
Recommended metrics / logs:
| Metric / Log | Purpose |
|--------------|---------|
| Lock acquisition latency | Detect contention hotspots |
| Conflict count per key | Identify oversharded or long critical sections |
| Average held duration | Tune TTL / identify overruns |
| Expired vs explicit releases | Spot abandoned locks |
| Wait time distribution (waitAndExecute) | Adjust `maxWait` / batch sizing |

Emit logs inside callbacks for critical resources:
```php
$lockManager->executeWithLock('feed:refresh', function () {
  logger()->info('Refreshing feed with exclusive lock');
  refreshFeed();
});
```

## Best Practices
1. Keep critical sections **small and fast**; push heavy work to queue jobs.
2. Use **idempotent** operations inside locks where feasible.
3. **Set realistic TTLs**: long enough for typical duration + buffer, short enough to auto‑clear orphans.
4. **Name locks semantically** (e.g. `user:42:avatar:regenerate`).
5. Avoid unbounded blocking waits; prefer `waitAndExecute` with a maxWait.
6. Refresh TTL sparingly and only when progress is confirmed.
7. Monitor contention; shard workloads if a single lock becomes a bottleneck.

## Troubleshooting
| Issue | Cause | Resolution |
|-------|-------|-----------|
| Frequent conflicts | Long critical section or too coarse key | Reduce work inside lock; add partitioning |
| Locks linger after crashes | TTL too long / auto-release disabled | Shorten TTL or enable autoRelease; add monitoring |
| High Redis usage | Excessive fine-grained keys | Aggregate tasks or batch operations |
| DB lock table growing | Stale rows not purged | Add cleanup job or enforce TTL expiry logic |
| File locks not shared across nodes | Non-shared filesystem | Switch to Redis or DB store |

## Cross‑Service References
- Scheduling: Prevent overlapping scheduled runs.
- Queues & Jobs: Use locks for singleton or leader election jobs.
- Caching: Pair with cache invalidation to avoid stampedes.
- Observability: Track conflict and wait metrics.
- Transactions: Combine database atomicity with lock guarding for external side effects.

---
**Summary:** Distributed locks give you coarse or fine-grained mutual exclusion with minimal ceremony. Start with `executeWithLock()` for safety, layer in monitoring, and graduate to Redis-backed locks as concurrency and horizontal scale increase.
