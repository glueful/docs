# Scheduling

Glueful ships with a cron–driven job scheduler that reads persisted jobs from the database and core jobs from configuration, evaluates cron expressions, and invokes registered callbacks/handlers. This guide explains how to configure schedules, run them manually or in a long‑lived worker loop, and monitor health. Where features are planned (CLI add/remove, history, parallel flags) but not yet implemented, they are explicitly marked.

At a high level:
- `JobScheduler` loads jobs from DB + `config/schedule.php` and in‑process registrations.
- Cron parsing via `cron/cron-expression` (standard 5‑field + @daily style shortcuts) determines due jobs.
- `queue:scheduler` command supports one‑off execution (`run`) and daemon/worker mode (`work`).
- Database tables (`scheduled_jobs`, `scheduled_job_executions`) persist definitions + execution metadata.
- Lock manager integration (if available) can enforce mutual exclusion (future enhancement for clustered nodes).
- Observability hooks (logging + future events) will surface failures, retries, and performance metrics.

> This scheduler is focused on **time‑based triggers**. Use the **Queues & Jobs** system for background processing and retry orchestration of heavier workloads.

## Core Concepts (At a Glance)
| Concept | Class / Config | Responsibility | Current Status / Notes |
|---------|----------------|----------------|------------------------|

| Execution Log (DB) | `scheduled_job_executions` table | Record start/end, status, timing | Table created; history display CLI not yet implemented |
| Config Jobs | `config/schedule.php` | Declarative core/system jobs | Loaded at scheduler instantiation |
| Callback Jobs | `JobScheduler::register()` | In‑process ephemeral jobs | Not persisted unless manually inserted into DB |

| Locking | `LockManagerInterface` | Prevent overlapping execution | Dependency injected; fine‑grained locking roadmap |
| Parallelism | `--parallel` CLI option | Intended concurrency control | Flag present; true parallel dispatch not wired yet |

## Configuration Snapshot
Location(s):
- Framework defaults / examples: `framework/config/schedule.php`
- Application override: `api-skeleton/config/schedule.php`

Example excerpt (application):
```php
return [
  'jobs' => [
    [
      'name' => 'session_cleaner',
      'schedule' => '0 0 * * *', // Daily midnight
      'handler_class' => 'Glueful\\Cron\\SessionCleaner',
      'parameters' => [],
      'description' => 'Cleans expired access & refresh tokens',
      'enabled' => env('SESSION_CLEANER_ENABLED', true),
      'persistence' => false,   // false = non‑persistent (in‑memory only)
      'timeout' => 300,
      'retry_attempts' => 3,
    ],
    // ...
  ],
  'settings' => [
    'enabled' => env('SCHEDULER_ENABLED', true),
    'max_concurrent_jobs' => env('MAX_CONCURRENT_JOBS', 5),
    'default_timeout' => env('DEFAULT_JOB_TIMEOUT', 300),
    'use_queue_for_all_jobs' => env('USE_QUEUE_FOR_SCHEDULED_JOBS', true),
  ],
];
```

## Quick Start
Run all due jobs once (respecting cron expressions):
```bash
php glueful queue:scheduler run
```
Force run all jobs regardless of schedule:
```bash
php glueful queue:scheduler run --force
```
Dry run (show what would execute without running):
```bash
php glueful queue:scheduler run --dry-run
```
Start worker/daemon loop (poll every 60s):
```bash
php glueful queue:scheduler work --interval=60
```
List scheduled jobs:
```bash
php glueful queue:scheduler list
```
Scheduler health check:
```bash
php glueful queue:scheduler health
```

> The `add`, `remove`, `enable`, `disable`, and `history` actions are currently placeholders in `SchedulerCommand` and will print messages indicating unimplemented functionality.

## Cron Expressions
The scheduler uses standard 5‑part cron expressions: `minute hour day-of-month month day-of-week` plus shortcut macros.

Supported shortcuts (expanded before evaluation):
```
@yearly  -> 0 0 1 1 *
@monthly -> 0 0 1 * *
@weekly  -> 0 0 * * 0
@daily   -> 0 0 * * *
@hourly  -> 0 * * * *
```

Example: Run every 15 minutes between 9AM–5PM weekdays:
```
*/15 9-17 * * 1-5
```

Use an external cron expression validator for complex patterns; current validation in `SchedulerCommand` only checks the part count (`validateCronExpression` = 5 tokens). A more robust parser is used at execution time (`CronExpression`).

## Defining Jobs
### Declarative (Config Based)
Add entries to `config/schedule.php` `jobs` array. Fields commonly used:
| Field | Meaning |
|-------|---------|
| name | Unique identifier |
| schedule | Cron expression or macro |
| handler_class | Fully-qualified class containing job logic |
| parameters | Arbitrary associative array passed to handler (implementation-specific) |
| description | Human summary |
| enabled | Boolean toggle |
| persistence | Whether to persist to DB (future enhancement; currently DB registration logic partially present) |
| timeout | Execution timeout budget in seconds |
| retry_attempts | Planned retry count (implementation dependent) |

### Programmatic (Callback Based)
Register an in‑memory callback during bootstrapping (e.g. service provider):
```php
use Glueful\Scheduler\JobScheduler;

app(JobScheduler::class)->register('@hourly', function () {
    // Your recurring task logic
    cleanupTempFiles();
}, 'hourly-temp-clean');
```
These jobs are not automatically persisted; they exist only for the lifetime of the process that registered them.

## Execution Modes
| Mode | CLI Action | Behavior |
|------|------------|----------|
| One‑off | `run` | Evaluates all cron expressions once; runs due jobs only (or all with --force) |
| Worker Loop | `work` | Sleeps between cycles (`--interval`), repeatedly evaluating and executing due jobs |

Worker loop metrics: uptime, completed run count, average interval (displayed upon exit). Use process supervision (systemd, container orchestrator) to restart on failure.

### Parallelism
`--parallel` option exists but the current implementation executes jobs sequentially. This guide will update once true parallel dispatch / process forking is added. Plan: spawn limited concurrent workers honoring `--parallel` and `max_concurrent_jobs` setting.

## Locking & Idempotency
`JobScheduler` accepts an optional `LockManagerInterface`, establishing the foundation for distributed locks to prevent overlapping runs in multi‑instance deployments. Current code initializes with the lock manager but does not yet wrap each job execution with a distributed lock or idempotency token. Roadmap: per‑job lock key (e.g. `scheduler:{job_name}`) acquired before execution; skipped if already locked.

When writing job logic:
- Make operations idempotent (safe to run twice) where feasible.
- Use database transactions or compare‑and‑swap semantics for stateful mutations.
- Defer long, failure‑prone work to the **Queues & Jobs** system; scheduled job enqueues background job(s) then exits quickly.

## Persistence & Tables
Tables are auto‑created if missing:
- `scheduled_jobs`: `uuid`, `name`, `schedule`, `handler_class`, `parameters` (JSON), `is_enabled`, `last_run`, `next_run`, timestamps.
- `scheduled_job_executions`: execution metadata (start, end, status, messages) — available for future history reporting.

`JobScheduler` loads enabled jobs into memory on construction via `loadJobsFromDatabase()` and `loadCoreJobsFromConfig()`. After each run, it updates `last_run` and computes the next occurrence using `CronExpression::getNextRunDate()`.

## Monitoring & Health
Use:
```bash
php glueful queue:scheduler status
```
This shows counts (total, enabled, disabled, running, idle) and a preview of upcoming jobs (placeholder for now — next run calculation partial). Health command (`health`) performs checks:
- No jobs scheduled (warning)
- Invalid cron expressions (issue)
- System load > threshold (warning)

Planned enhancements:
- Emit framework Events (e.g. `ScheduledJobStarting`, `ScheduledJobCompleted`, `ScheduledJobFailed`).
- Aggregate execution duration percentiles and failure rates for Observability dashboards.

## Error Handling & Retries
Current implementation runs callbacks/handlers and logs errors; structured retry logic (`retry_attempts`) and failure notifications are planned. For tasks requiring robust retry/backoff now, schedule a lightweight job that dispatches a queue job with the existing **Queues & Jobs** retry semantics.

## Troubleshooting
| Symptom | Possible Cause | Resolution |
|---------|----------------|-----------|
| No jobs run | Cron expressions not due / scheduler disabled | Use `--force` to verify; check `config/schedule.php` enabled flags |
| Health shows invalid cron | Typo in expression | Validate with external cron tool; fix schedule string |
| Parallel flag ignored | Feature not implemented | Remove flag for now; await upcoming release |
| add/remove actions do nothing | Placeholder feature | Define jobs in config or code instead |
| Repeated duplicate execution in clustered env | Missing distributed lock | Await lock-wrapped execution or add manual lock in handler |
| Long-running job blocks others | Sequential execution design | Offload heavy logic to queued job; keep scheduled job thin |

## Roadmap / Planned Enhancements
- Implement dynamic job management (add/remove/enable/disable) persisting changes to DB.
- Rich execution history: display last N runs, durations, failure reasons.
- True parallel execution with `--parallel` and per‑job concurrency limits.
- Distributed locking per job to avoid overlap across multiple nodes.
- Event emission for lifecycle stages feeding Observability & Notifications.
- Retry policy enforcement using `retry_attempts` config values.
- Per‑job tagging and queue dispatch integration (schedule triggers queue jobs instead of inline logic).
- Cron next-run preview & calendar export tooling.

## Cross‑Service References
- Queues & Jobs: Use for heavy / retryable background processing triggered by schedules.
- Events & Listeners: Planned job lifecycle events will integrate here.
- Observability: Health + future metrics & tracing for scheduled executions.
- Locks: Distributed lock manager for safe multi-instance scheduling.
- Uploads & Storage: Schedule periodic cleanup / archival tasks.

---
**Summary:** The scheduler provides a foundation for cron‑based recurring tasks with a clear path to richer management (dynamic job CRUD, history, parallelism, events). Define jobs declaratively or programmatically today; offload complex, long-running, or failure‑sensitive work to the queue layer while the scheduler orchestrates timing.
