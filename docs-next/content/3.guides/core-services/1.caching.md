# Caching

Glueful's caching layer reduces latency, lowers database load, and enables responsive APIs under burst traffic. This guide focuses on practical usage patterns: choosing a driver, applying read‑through/write‑through strategies, tagging for grouped invalidation, preventing stampedes, and preparing for edge/CDN distribution.

## When to Use Cache
Use caching when repeated reads of expensive computations or database queries degrade latency. Avoid caching data that changes every request or is already O(1) to compute.

## Core Concepts
| Concept | Summary | Typical Use |
|---------|---------|-------------|
| Read‑Through | Populate on miss via `remember()` | Entity/profile hydration |
| Write‑Through | Update cache when source of truth mutates | Post-create/update flows |
| Tagging | Attach logical tags for bulk invalidation | Invalidate all user:* after role change |
| Stampede Protection | Single flight ensures one recompute | Hot keys under concurrent load |
| SetNX Locks | Coarse-grain contention control | Thundering herd prevention |
| Edge Layer | CDN caches immutable / versioned payloads | Public product/catalog data |

## Quick Start
```php
use Glueful\Cache\CacheFactory;

$cache = CacheFactory::create();
$user = $cache->remember('user:'.$id, function() use ($repo, $id) {
    return $repo->find($id); // Only hit DB on miss
}, 600); // TTL seconds
```

## Driver Selection
| Driver | Strengths | Considerations |
|--------|-----------|----------------|
| Redis | Rich ops (sorted sets, pattern delete), fastest invalidation | External service dependency |
| Memcached | Simple, low‑latency, horizontal | Fewer introspection features |
| File | Zero infra, good for dev/tests | Not ideal for multi-node prod |

Configuration lives in `config/cache.php` (keys: `default`, `stores.*`, `stampede_protection.*`, `edge.*`).

## Read‑Through Pattern
```php
$product = $cache->remember('product:'.$sku, function() use ($repo, $sku) {
    return $repo->findBySku($sku);
}, 900);
```

## Write‑Through Pattern
```php
$repo->update($id, $payload);
$cache->set('user:'.$id, $repo->find($id), 600); // keep cache warm
```

## Tagging & Group Invalidation
```php
// Save with tags
$cache->set('user:'.$id, $data, 600);
$cache->addTags('user:'.$id, ['user:'.$id, 'role:'.$data['role']]);

// Invalidate everything for a user (e.g. password change)
$cache->invalidateTags(['user:'.$id]);
```

## Stampede Protection
`remember()` internally leverages atomic operations to ensure only one recalculation when enabled in config (`stampede_protection.enabled`).
```php
$profile = $cache->remember('profile:'.$id, fn() => $service->hydrate($id), 300);
```

## Safe Operations with Fallback
```php
use Glueful\Helpers\CacheHelper;

$cache = CacheHelper::createCacheInstance(); // returns null if backend down
$value = CacheHelper::safeExecute($cache, fn($c) => $c->get('feature:flag'), false);
```

## Pattern Deletion
```php
$cache->deletePattern('session:*'); // Redis/File drivers
```

## Edge Caching Hints
Use HTTP `Cache-Control: public, max-age=60, stale-while-revalidate=120` with versioned URLs. Coordinate invalidation by embedding content hashes.

::: tip
Prefer shorter TTL + cheap recompute over very long TTL + forced flushes—improves freshness and simplifies invalidation strategy.
:::

::: warning
Do not cache authorization-scoped data at the edge unless it is explicitly anonymized or Vary headers are set correctly.
:::

## Monitoring & Metrics
Track hit ratio, stampede misses, and invalidation volume. Low hit ratio (<60%) usually means: key churn, over-personalization, or overly short TTLs.

## Common Patterns
| Pattern | Example |
|---------|---------|
| Bulk Prewarm | Iterate hot keys at deploy and `set()` each |
| Negative Cache | Cache known-missing IDs briefly to dampen DB load |
| Sliding TTL (Manual) | On read, re-`set()` with same value and new TTL |

### Caching-Specific Issues
| Symptom | Cause | Action |
|---------|-------|--------|
| Low hit ratio | Key mismatch / missing prefix | Check `CACHE_PREFIX` and normalization |
| Frequent stampedes | Protection disabled / long recompute | Enable protection, break work into shards |
| Tag invalidation slow | Large tag sets on File driver | Prefer Redis for heavy tagging |
| Memory bloat | Unbounded value size | Compress value or persist only critical fields |
