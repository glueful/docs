# CLI & Console

Glueful wraps Symfony Console with dependency injection, grouped command namespaces, and rich helper methods. Use it to automate maintenance, migrations, background processing, inspections, and deployment workflows.

## At a Glance

- Symfony Console under the hood with DI-backed instantiation (`Application` + container).
- Command registry enumerated in `Application::$commands` (services resolved through container).
- Base class `Glueful\Console\BaseCommand` adds convenience: styled output, progress, tables, interactive prompts, production safety confirmation.
- Extension packages can contribute command classes (after extension cache rebuild).
- Roadmap: dynamic discovery via attributes, command tagging, config caching command, diagnostics (`dev:services`, `locks:list`).

## Core Architecture

| Component | Location | Responsibility |
|----------|----------|----------------|
| Console Entry Script | `bin/glueful` | Bootstraps framework, builds container, runs console application |
| Application | `src/Console/Application.php` | Registers commands, sets default command, manages DI integration |
| BaseCommand | `src/Console/BaseCommand.php` | Common helpers (IO styling, progress bars, interactive questions, container access) |
| Command Group Folders | `src/Console/Commands/*` | Logical grouping (Cache, Queue, Extensions, Security, System, Migrate, Generate, etc.) |
| Extension Commands | Extension `src/Console/Commands` (if present) | Add domain specific tooling |

## Discovering Commands

List all available commands:

```
php glueful
```

Filter by namespace (Symfony pattern):

```
php glueful list cache
php glueful list queue
```

After installing a new extension:

```
php glueful extensions:clear && php glueful extensions:cache
php glueful extensions:list
```

## Creating a Command

Minimal skeleton:

```php
<?php
namespace App\Console\Commands;

use Glueful\Console\BaseCommand;
use Symfony\Component\Console\Input\InputArgument;
use Symfony\Component\Console\Input\InputOption;

class GreetUserCommand extends BaseCommand
{
	protected static $defaultName = 'app:greet';
	protected static $defaultDescription = 'Greet a user by name';

	protected function configure(): void
	{
		$this->addArgument('name', InputArgument::REQUIRED, 'User name');
		$this->addOption('yell', 'y', InputOption::VALUE_NONE, 'Uppercase greeting');
	}

	protected function execute($input, $output): int
	{
		$name = $input->getArgument('name');
		$message = 'Hello ' . $name;
		if ($input->getOption('yell')) {
			$message = strtoupper($message) . '!';
		}
		$this->success($message);
		return self::SUCCESS;
	}
}
```

Register it by adding the class to a service provider that calls the console application's `addCommand()` or (roadmap) auto-discovery via future attributes. For now you can manually add to the console during a custom bootstrap or create an extension contributing it.

## Dependency Injection in Commands

Commands are resolved through the container—constructor type hints are fulfilled automatically. Use `$this->getService(FooService::class)` for late resolution or dynamic container keys via `getServiceDynamic()`.

Example service usage inside `execute()`:

```php
$notifier = $this->getService(\App\Services\NotificationService::class);
$notifier->sendWelcome($userId);
```

## Arguments & Options

| Use | Method | Notes |
|-----|-------|-------|
| Required arg | `$this->addArgument('id', InputArgument::REQUIRED)` | Order matters |
| Optional arg | `InputArgument::OPTIONAL` | Provide default in logic |
| Array arg | `InputArgument::IS_ARRAY` | Collect multiple values |
| Flag option | `$this->addOption('force', 'f', InputOption::VALUE_NONE)` | Boolean style |
| Value option | `InputOption::VALUE_REQUIRED` | Must be provided |
| Optional value option | `VALUE_OPTIONAL` | `null` if missing |

Access via `$input->getArgument('id')` / `$input->getOption('force')` (Symfony standard).

## Interactive I/O Helpers

`BaseCommand` wraps SymfonyStyle for consistent formatting:

| Method | Purpose |
|--------|---------|
| `success()` / `error()` / `warning()` / `info()` | Styled status blocks |
| `note()` / `tip()` | Guidance & hints |
| `ask()` / `secret()` / `confirm()` / `choice()` | Interactive questions |
| `table($headers,$rows)` | Tabular output |
| `progressBar($steps, fn($bar)=>{ ... })` | Visual progress for loops |

All methods are purely presentation—they do not alter exit codes.

## Long-Running & Background Tasks

Patterns:

| Scenario | Recommendation |
|----------|----------------|
| Queue worker | Use `queue:work` + supervisor/process manager |
| Scheduler loop | `queue:scheduler work` separate process |
| Continuous metrics export (future) | Plan dedicated command with graceful shutdown signals |
| Large batch operations | Use `progressBar()` and periodic memory / time logging |

Graceful termination: leverage OS signals (future enhancement—currently rely on external process control to stop workers cleanly).

## Production Safety

`BaseCommand::confirmProduction()` guards destructive operations by re-prompting when `APP_ENV=production` (internally checks `config('app.env')`). Use before schema resets, data purges, or mass reprocessing.

```php
if (!$this->confirmProduction('reset the database')) {
  return self::FAILURE;
}
```

## Extension Integration

Extension command classes (namespaced under their package) are added to the registry after rebuilding the extension cache. Keep commands cohesive: one responsibility, clear name prefix (e.g., `email:retry`, `locks:stats`).

## Output Patterns

Prefer machine-friendly structures for automation contexts:

| Pattern | Example |
|---------|---------|
| Key=Value lines | `status=ok duration_ms=153` |
| JSON (single line) | `{"status":"ok","processed":42}` |
| Tables (interactive only) | Human inspection sessions |

## Best Practices

| Practice | Benefit |
|----------|---------|
| Single responsibility commands | Easier composability in scripts |
| Consistent naming (`domain:verb`) | Discoverability via namespace filtering |
| Idempotent re-runs | Safe retry after partial failure |
| Honor non-zero exit codes | CI/CD failure propagation |
| Avoid excessive output at default verbosity | Cleaner logs; use `-v`, `-vv` for detail |
| Wrap long loops with progress + periodic flush | Feedback + resource control |

## Troubleshooting

| Symptom | Likely Cause | Action |
|---------|-------------|--------|
| Command not listed | Not registered in `Application::$commands` and not added dynamically | Add class via `addCommand()` or extension cache refresh |
| DI failure resolving service | Missing binding or provider | Register service in container / service provider |
| Interactive prompts freeze in CI | Non-interactive environment | Add `--no-interaction` or bypass questions with options |
| Progress bar overwrites logs | Piped output environment | Disable progress or use plain logging mode |

## Roadmap

1. Attribute/annotation based auto-discovery (no manual registry edits).
2. Command tagging & `list --tags=maintenance` filtering.
3. JSON log formatter integration across all commands.
4. Diagnostics commands (`dev:services`, `locks:list`, `health:check`).
5. Graceful signal handling for long-running processes.
6. Config caching (`config:cache`) & warm boot.
7. Generators expansion (models, jobs, events).

## Summary

The console layer marries Symfony’s mature interaction model with Glueful’s DI and helper ergonomics. Start simple—one focused command—and layer interactivity, progress, and safety checks as complexity grows. Use extensions to ship domain-specific tooling without polluting core application space.
