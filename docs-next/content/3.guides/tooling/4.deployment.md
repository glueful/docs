# Deployment

This guide outlines deployment targets, build steps, runtime topology, zero‑downtime strategies, and operational safeguards for Glueful-based applications and extensions.

## At a Glance

- Stateless HTTP layer: fronted by web server / gateway (Nginx + PHP-FPM, Caddy, or containerized).
- Single entrypoint: `public/index.php` boots the app and dispatches a Symfony HTTP request lifecycle.
- Background processes: queue workers, scheduler loop, (future) metrics/export tasks.
- Configuration via environment; no mutable code-time config needed at deploy.
- Roadmap: precompiled config cache, build artifact slimming, health/ready probes, blue/green deploy helper commands.

## Typical Deployment Workflow

| Phase | Action | Output |
|-------|--------|--------|
| 1 | Fetch source (Git clone / checkout tag) | Working tree |
| 2 | Install dependencies (`composer install --no-dev --optimize-autoloader`) | Optimized vendor tree |
| 3 | (Optional) Build assets (if serving docs/frontends) | Compiled static assets |
| 4 | Run tests & static analysis in CI | Confidence to proceed |
| 5 | Package (tar/zip container image) | Immutable artifact |
| 6 | Release to target (copy artifact / push image) | Staged version |
| 7 | Run migrations (if required) | Updated schema |
| 8 | Warm caches (future `config:cache`, route cache) | Faster cold start |
| 9 | Start services (FPM pool, workers, scheduler) | Live traffic |

## Runtime Topology

```
	+-------------+        +-----------------+
Client -> CDN / WAF ->| Nginx / Reverse Proxy |-> PHP-FPM Pool -> Glueful App (public/index.php)
	+-------------+        +-----------------+
				   |    |    |
				   |    |    +-> Queue Workers (queue:work)
				   |    +------> Scheduler (queue:scheduler)
				   +----------> Ext. Services (DB, Cache, Storage)
```

## Supported Execution Models

| Model | Summary | When to Choose |
|-------|---------|----------------|
| PHP-FPM + Nginx | Standard robust setup | Most production workloads |
| Caddy + FPM | Simplified TLS + HTTP/2 | Small teams needing simpler config |
| Container (Docker) | Immutable artifact & infra parity | Multi-env consistency, orchestration |
| RoadRunner / Swoole (Roadmap) | Persistent worker model | High throughput, reduced bootstrap cost |

Roadrunner/Swoole integration is a forward-looking optimization; confirm framework lifecycle hooks support before adopting.

## Environment Configuration

Inject environment variables at container runtime / process manager (systemd, Kubernetes, ECS). Do not commit sensitive values. Refer to the Configuration guide for key variables. Minimum recommended set:

| Variable | Purpose |
|----------|---------|
| `APP_ENV=production` | Enables production safeguards |
| `APP_KEY` | Cryptographic features |
| `DB_DRIVER` + specific `DB_*` | Database connectivity |
| `CACHE_DRIVER` | Primary cache store |
| `LOG_LEVEL` | Log verbosity control |
| `FORCE_HTTPS=true` | Enforce secure URLs |

## Zero-Downtime Strategies

| Strategy | Concept | Notes |
|----------|---------|-------|
| Blue/Green | Two identical stacks; flip load balancer | Safest for schema-compatible releases |
| Rolling | Replace instances sequentially | Ensure backward-compatible schema first |
| Canary | Route small traffic slice to new version | Requires observability to compare KPIs |

Migrations should be additive & backward-compatible before routing traffic (e.g., add columns nullable, deploy code, backfill, enforce constraints later).

## Database Migrations

- Run migrations before enabling new logic requiring schema changes.
- Always back up (or snapshot) critical data stores before destructive operations.
- Use idempotent migration scripts; detect prior application gracefully.
- Defer heavy backfills to background jobs (queue) to avoid deploy latency.

## Queues & Scheduler

| Process | Command | Scaling |
|---------|---------|---------|
| Worker | `queue:work` | Horizontal: more processes/containers |
| Auto-scale (future) | `queue:auto-scale` | Roadmap: metrics-driven concurrency adjustments |
| Scheduler Loop | `queue:scheduler` | Single (or HA with leader election – roadmap) |

Use a process supervisor (systemd, Supervisor, Kubernetes deployment) to keep workers running and restart on failure. Ensure idempotent job handlers to tolerate retries.

## Observability Essentials

| Aspect | Recommendation |
|--------|----------------|
| Logs | Ship to central store (ELK, Loki, CloudWatch). Separate framework vs application channels. |
| Metrics (roadmap) | Capture request latency, worker throughput, failure counts. |
| Traces (roadmap) | Integrate OpenTelemetry exporter for distributed tracing. |
| Health | Implement simple readiness endpoint (boot success & dependency pings) – roadmap for `system:check --format=json`. |

Correlate CLI-initiated batch logs with a correlation ID (pass env var or generate in command) for traceability.

## Security Hardening

| Layer | Measure |
|-------|--------|
| Transport | Terminate TLS at load balancer / ingress; force HTTPS internally (`force_https`). |
| Headers | Add security headers at proxy (CSP, HSTS) + sanitization at app level. |
| Secrets | Environment / secrets manager; rotate `APP_KEY` with re-encryption plan. |
| Surface | Disable API docs in production (auto). |
| Logging | Avoid sensitive data in logs; apply field filters (roadmap). |

## Scaling Approaches

| Dimension | Method | Trade-offs |
|-----------|--------|-----------|
| App (horizontal) | Increase PHP-FPM workers / container replicas | Watch DB connection pool saturation |
| Cache | Promote to Redis / enable distributed caching | Operational overhead |
| Database | Read replicas, connection pooling tuning | Replica lag complexity |
| Queue throughput | More workers; partition queues | Message ordering constraints |
| Static assets | CDN + immutable cache headers | Invalidation strategy |

Profile first—premature optimization hides bottlenecks.

## Rolling Back

| Asset | Rollback Step |
|-------|---------------|
| Code | Re-deploy previous artifact or switch load balancer target |
| DB (additive changes) | Usually safe—leave in place |
| DB (destructive) | Restore from backup/snapshot (ensure tested automation) |
| Cache keys | Flush targeted namespaces if inconsistent state |

Design migrations to be rollback-friendly by preferring additive patterns.

## Disaster Recovery (DR) Basics

| Component | DR Consideration |
|-----------|------------------|
| Backups | Automate daily DB + weekly full with retention policy |
| Offsite | Replicate critical backups to separate region/account |
| Restore Testing | Quarterly restore drills validate scripts |
| Config | Store environment variable manifests (without secrets) in version control |
| Logs | Retain structured logs for incident forensics |

## Deployment Checklist

| Item | Status |
|------|--------|
| Tests green (unit/integration) | ☐ |
| Static analysis & lint pass | ☐ |
| Migrations reviewed & additive | ☐ |
| Backup taken (pre-migration) | ☐ |
| Environment variables verified | ☐ |
| Queues drained or safe for rolling worker restart | ☐ |
| Observability endpoints healthy (baseline) | ☐ |
| Rollback plan documented | ☐ |
| Post-deploy smoke tests executed | ☐ |

## Roadmap

1. `config:cache`, `route:cache` commands for warm start.
2. Health & readiness probes (`system:check --readiness`).
3. First-class RoadRunner/Swoole worker mode adapter.
4. Auto-scale queue worker controller using backlog & latency metrics.
5. Secrets provider integration & rotation CLI.
6. Deployment manifest generator summarizing versions, migrations, config deltas.

## Summary

Deploying Glueful centers on immutable artifacts, environment-driven configuration, and horizontally scalable stateless processes. Layer in background workers, scheduler, and observability. Favor additive schema changes, plan for rollback, monitor key health metrics, and adopt upcoming cache & probing features to reduce cold start time and improve confidence.
