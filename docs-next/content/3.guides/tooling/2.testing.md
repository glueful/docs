# Testing

A lean but expressive testing stack helps keep framework and extension code safe to evolve. Glueful uses PHPUnit (10.x) with a bootstrap that provisions a lightweight container, mock logger, filesystem paths, and test environment variables.

## Philosophy

- Fast feedback: keep most logic at pure unit or container-light integration level.
- Deterministic: avoid ordering dependencies; no hidden global state beyond the explicit container.
- Hermetic: in-memory or temp filesystem over network services whenever practical.
- Intent revealing: test names describe behavior, not implementation.
- Progressive layering: add integration tests only where cross-component wiring matters.

## Test Pyramid (Recommended Balance)

| Layer | Goal | Ratio Target |
|-------|------|--------------|
| Unit | Validate isolated logic & contracts | ~60% |
| Integration | Container wiring, routing, schedulers | ~25% |
| Feature / End-to-End | CLI surface, complex flows | ~10% |
| Non-functional (perf, load) | Roadmap; stability thresholds | ~5% (future) |

## Configuration Overview

File: `phpunit.xml.dist`

Key points:

- Bootstrap: `tests/bootstrap.php` sets autoloaders, container, env.
- Single declared suite `Core` (additional suites can be added when splitting domains or performance/stress tests).
- Caching enabled via `.phpunit.cache` for speed.

To create a project-specific override copy to `phpunit.xml` and adjust.

## Bootstrap Mechanics

`tests/bootstrap.php` responsibilities:

| Concern | Mechanism |
|---------|-----------|
| Autoload | Attempts framework + parent vendor autoloaders |
| Container | Instantiates `Glueful\Container\Container` with a mocked `LogManager` |
| Globals | Stores container in `$GLOBALS['container']` and helpers `app()` / `config()` |
| Env | Sets `APP_ENV=testing` plus DB placeholders |
| Filesystem | Creates cache/log temp directories |
| Exception Handling | Puts `ExceptionHandler` into test mode (if class exists) |
| Timezone | Forces UTC for deterministic date handling |

## Directory Structure (Observed)

| Path | Purpose |
|------|---------|
| `tests/Unit/*` | Pure logic tests (routing, extensions, container loaders) |
| `tests/Integration/*` | Cross-component behavior (router, scheduler, storage, boot) |
| `tests/Feature/CliIntegrationTest.php` | End-to-end CLI surface tests using Symfony Process |
| `tests/Core` | Core-level tests (route caching, boot) referenced by suite |

You can introduce `tests/Feature/Http` or `tests/Performance` as the framework grows.

## Base Test Utilities

If you need shared helpers, introduce a `tests/TestCase.php` extending `PHPUnit\Framework\TestCase` to centralize container access, temporary path helpers, or custom assertions.

Suggested pattern:

```php
abstract class TestCase extends \PHPUnit\Framework\TestCase
{
	protected function container(): \Psr\Container\ContainerInterface
	{
		return $GLOBALS['container'];
	}

	protected function fakePath(string $segment): string
	{
		$base = sys_get_temp_dir() . '/glueful-tests';
		@mkdir($base, 0775, true);
		return $base . '/' . ltrim($segment, '/');
	}
}
```

## Environment & Database Strategy

Current bootstrap seeds generic DB env vars but integration tests frequently rely on in-memory or stub data structures. Recommendations:

| Scenario | Strategy |
|----------|----------|
| Pure unit | No DB touch—inject fakes or simple arrays |
| Transient persistence | SQLite in-memory (`DB_DRIVER=sqlite`, `:memory:`) |
| Migration testing | Temp SQLite file per test class (cleanup in `tearDown()`) |
| Concurrency / locking | Use real lock store (e.g., file or redis) only in a dedicated integration group |

Keep destructive tests out of the default run by tagging them and using `--exclude-group` or `--group` filters.

## Fixtures & Test Data

Patterns (none are mandatory yet):

| Approach | Use When |
|----------|---------|
| Inline arrays | Simple value objects, configuration maps |
| Factory helper methods | Multiple variants of same entity |
| Builder pattern | Complex nested DTOs |
| JSON fixture files | Large static payloads (cache parsed representation) |

Avoid over-engineering early—promote factories only after duplication appears 3+ times.

## Testing Console Commands

Use Symfony Process for black-box invocation (as in `CliIntegrationTest`). Key points:

```php
$process = new Process(['php', $bin, 'list']);
$process->setEnv([
  'APP_ENV' => 'testing',
  'CACHE_DRIVER' => 'array',
  'LOG_TO_FILE' => 'false',
]);
$process->run();
$this->assertTrue($process->isSuccessful(), $process->getErrorOutput());
```

Prefer targeted output assertions (e.g., specific command names) over entire snapshot comparisons to reduce brittleness.

For unit-level command tests (faster): instantiate the command class directly, inject required dependencies (via container or mocks), and execute using a `CommandTester` (Symfony Console component) once added to dependencies. Roadmap item: provide a small wrapper to simplify this pattern.

## Testing Scheduling & Queue Behavior

The scheduler integration test (`SchedulerIntegrationTest.php`) exemplifies multi-step coordination. Guidelines:

| Concern | Recommendation |
|---------|----------------|
| Time-based triggers | Inject a clock abstraction (roadmap) or use deterministic timestamps |
| Idempotency | Re-run job scheduling sequence; assert no duplication |
| Locking | Simulate concurrent acquisition with two instances if lock store implemented |
| Backoff / retries | Introduce retry policy test once notification/queue retry logic formalized |

## Assertions & Custom Helpers

Consider adding domain assertions to reduce repetition:

```php
trait AssertsConsole
{
	protected function assertCommandListed(string $needle, string $output): void
	{
		$this->assertStringContainsString($needle, $output, "Expected command '$needle' not found in list output");
	}
}
```

## Running Tests

Basic run:

```
vendor/bin/phpunit
```

Filter by directory or test name:

```
vendor/bin/phpunit --testsuite Core
vendor/bin/phpunit --filter SchedulerIntegrationTest
```

Stop on failure for tight loops:

```
vendor/bin/phpunit --stop-on-failure
```

## Coverage & Metrics

Coverage tooling is optional (not enforced in current config). To enable locally:

1. Ensure Xdebug or PCOV installed.
2. Run with `--coverage-html build/coverage`.
3. Track trends rather than absolute % early; focus on critical service surfaces (routing, locking, scheduler, console bootstrap).

Roadmap: integrate minimum coverage threshold & mutation testing (e.g., Infection) once stability matures.

## Flakiness Prevention

| Source | Mitigation |
|--------|-----------|
| Time-dependent | Fixed clock abstraction / freeze time helpers |
| Randomness | Seed RNG (`mt_srand(1)`) in bootstrap for deterministic sequences |
| Temp files | Use unique per-test tmp dirs; cleanup in `tearDown()` |
| External processes | Keep process timeouts short; assert exit codes |

## Troubleshooting

| Symptom | Cause | Resolution |
|---------|-------|------------|
| Autoload not found | Vendor install skipped | Run `composer install` |
| Command list missing expected name | Command not registered / cache not rebuilt | Rebuild extensions, inspect `Application::$commands` |
| Intermittent scheduler test failure | Time drift / non-deterministic sleep | Replace real time with fixed timestamps |
| Memory leak over suite | Large objects retained statically | Clear static caches in `tearDownAfterClass()` |
