# Authentication API

Reference for authentication flows and token handling.

## Overview
Glueful's authentication layer provides a provider-driven pipeline for validating incoming requests, establishing a user context, and issuing/verifying token credentials. It is intentionally lightweight: no global session state, clear separation of responsibilities (provider vs token services), and composable PHP 8 attributes for access control.

### Core Concepts
- Provider: Pluggable strategy that can authenticate a request (e.g. JWT, API Key). Providers expose capabilities like token generation, validation, refresh, and format detection.
- Token Services: Lower-level helpers used by providers (e.g. `JWTService`, `TokenStorageService`) for cryptographic operations or persistence.
- Attributes: Declarative access control (`#[RequiresPermission]`, `#[RequiresRole]`) applied to controller classes or methods.
- Middleware: Executes the authentication sequence and enriches the request (`AuthMiddleware`).

## Request Authentication Flow
1. Incoming HTTP request hits routing layer.
2. `AuthMiddleware` iterates configured providers (order matters) until one successfully authenticates or all fail.
3. On success:
   - User/session data is attached to request attributes (`authenticated`, `user_id`, `user_data`).
   - Provider name recorded for downstream logic.
4. Authorization phase (if controller/method has attributes):
   - Gather attached attributes (roles / permissions) and evaluate with permission subsystem (if available).
5. Controller action executes with authenticated context.
6. Downstream layers (logging, observability) can inspect enriched request metadata.

If all providers fail silently (no hard error), the request is considered unauthenticated and may still reach endpoints that do not require auth.

## Token Lifecycle
| Aspect | Access Token | Refresh Token / API Key |
|--------|--------------|--------------------------|
| Storage | Not persisted (JWT self-contained) or referenced via session UUID | Persisted via `TokenStorageService` or as user API key |
| Rotation | New pair on refresh or login | API Key rarely rotates; refresh token exchanged for new access (JWT) |
| Invalidation | Natural expiry + explicit revocation via storage lookup | Delete session / revoke key |
| Usage | Sent in `Authorization: Bearer <token>` header | Same header or `X-API-Key` / query param (API key) |
| Security Notes | Short lifetime recommended | Treat API keys like long-lived sensitive secrets |

### Refresh Flow (JWT)
1. Client sends refresh token (HTTP-only cookie or Authorization header depending on integration).
2. Provider validates refresh token against stored session.
3. New token pair generated by `TokenManager` (access + refresh) and persisted.
4. Old refresh token invalidated (rotated) to prevent replay.

## Quick Start Examples

### Authenticating a Request (JWT)
```php
$provider = new Glueful\Auth\JwtAuthenticationProvider();
$userData = $provider->authenticate($request);
if ($userData === null) {
    return new JsonResponse(['error' => $provider->getError()], 401);
}
```

### Generating a Token Pair
```php
$provider = new Glueful\Auth\JwtAuthenticationProvider();
$tokens = $provider->generateTokens(['uuid' => $userId, 'email' => $email]);
// ['access_token' => '...', 'refresh_token' => '...', 'expires_in' => 3600]
```

### Protecting a Controller Method
```php
use Glueful\Auth\Attributes\RequiresPermission;
use Glueful\Auth\Attributes\RequiresRole;

class PostController {
    #[RequiresRole('editor')]
    #[RequiresPermission('posts.publish')]
    public function publish(int $id) { /* ... */ }
}
```

### Checking Admin in Code (Provider-Aware)
```php
$provider = new Glueful\Auth\JwtAuthenticationProvider();
if ($provider->isAdmin($userData)) {
    // privileged path
}
```

## Best Practices & Tips
- Keep access tokens short-lived; rely on refresh for longevity.
- Always validate refresh tokens against server-side state (`TokenStorageService`).
- Avoid leaking API keys in URLs; prefer headers.
- Combine role + permission attributes for layered defense (broad role + granular permission).
- Log authentication failures with enough context for observability, but never log raw tokens.
- Revoke tokens immediately on credential rotation or suspicious activity.

## Error Handling Patterns
| Scenario | Recommended Response | Notes |
|----------|----------------------|-------|
| Missing token | 401 + generic message | Avoid revealing which credential missing |
| Expired token | 401 + token expired | Prompt client to refresh |
| Invalid signature | 401 generic | Do not differentiate signature vs format publicly |
| Permission denied | 403 | Authenticated but not authorized |

## Extending Authentication
To add a new provider:
1. Implement `AuthenticationProviderInterface`.
2. Provide `authenticate()`, `canHandleToken()`, `validateToken()`, and optionally `generateTokens()` / `refreshTokens()`.
3. Register or ensure discovery (if auto-loaded) so middleware can iterate it.
4. Add docblocks — they will surface in the generated Providers table automatically.
