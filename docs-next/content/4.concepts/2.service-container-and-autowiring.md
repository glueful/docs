# Service Container & Autowiring

The service container is the backbone of Glueful's runtime: every framework capability (routing, permissions, logging, tasks, queue, etc.) is exposed as a resolved service. This concept explains the mental model, the definition types, provider layering, autowiring algorithm, tagging system, compilation path, and extension points—plus guidance and anti‑patterns.

## At a Glance

| Aspect | Implementation | Notes |
| ------ | -------------- | ----- |
| PSR Compliance | Implements `Psr\Container\ContainerInterface` | Custom lightweight runtime container. |
| Definitions | Value, Factory, Alias, Autowire, TaggedIterator | All implement `DefinitionInterface` with `resolve()` + `isShared()`. |
| Sharing (Singleton) | Per-ID caching if `isShared() === true` | `ValueDefinition` & most autowired services shared; alias never shared. |
| Circular Detection | Runtime guard with resolving stack | Throws `ContainerException` with chain path. |
| Scoped Overrides | `with([...])` creates child w/ delegate | Child resolves new/override first, then delegates. Ideal for tests. |
| Tagging | `TagCollector` + `TaggedIteratorDefinition` | Deterministic priority ordering. |
| Providers | Classes extending `BaseServiceProvider` | Contribute defs + declare tags. |
| Extension Loading | Static `defs()` or DSL `services()` in extensions | Unified by `ContainerFactory`. |
| Autowiring | Reflection of constructor + optional `#[Inject]` attribute | Falls back to defaults/null or throws. |
| Param Injection | `param.bag` (`ParamBag`) + `#[Inject(param: "key")]` | Bag is a simple immutable parameter store. |
| Compilation | `ContainerCompiler` emits optimized PHP class | Only supports Value, Autowire, Alias, TaggedIterator. |
| Unsupported in Compile | FactoryDefinition, unknown Definition types | Must convert to supported style or runtime fallback. |
| Middleware Aliases | Defined via `AliasDefinition` in `CoreProvider` | e.g. `auth`, `rate_limit`, `metrics`, `tracing`, etc. |

## Mental Model

Think of the container as a two-stage resolver pipeline:

1. Definition Lookup: Find a `DefinitionInterface` for the requested ID (or short circuit from singleton cache, or delegate).
2. Definition Resolution: Call `resolve($container)` which may construct (autowire), forward (`AliasDefinition`), hydrate tagged collections, or run a factory closure.

If the definition declares itself shared (`isShared() === true`), the resolved value is cached in the `$singletons` map. A second request returns the cached instance with zero additional logic.

```
request get(id)
	-> singleton? return
	-> definition exists? resolve()
			 -> constructing (autowire) / returning value / executing factory / iterating tags
			 -> shared? store in singletons
	-> delegate? try delegate
	-> else NotFoundException
```

## Definition Types

| Type | Purpose | Shared? | Typical Use |
| ---- | ------- | ------- | ----------- |
| ValueDefinition | Constant scalar/object config or lightweight immutable service instance | Always | Pre-built config objects, static maps. |
| FactoryDefinition | Arbitrary closure logic and conditional setup | Configurable (default shared) | When construction needs branching, external IO, or late config lookups. |
| AutowireDefinition | Reflection-based constructor injection by FQCN | Usually shared | Core stateless services, middleware classes, pure orchestrators. |
| AliasDefinition | Alternate ID pointing to target ID | Never (delegates target's cache) | Interface → implementation, human-friendly string aliases (middleware). |
| TaggedIteratorDefinition | Deterministic ordered list of tagged services | Always | Pipelines, plugin chains, background warmups. |

Every definition implements:

* `resolve(ContainerInterface $c): mixed` – produce the value
* `isShared(): bool` – decides singleton caching semantics

### Aliases
An alias is cheap indirection. Because `isShared()` returns false for aliases, the container never stores an alias result; it forwards to the target each time, leveraging the target's own sharing policy. This ensures sharing is centralized at the canonical ID.

### Factories
Factories let you insert conditional logic, environment detection, or adapter selection. Prefer an `AutowireDefinition` if the construction is a straight new + dependency graph.

### Autowire Definitions
`AutowireDefinition` stores an ID + class + share flag. Construction is delegated to a shared `ReflectionResolver`, which caches constructor reflections (`\ReflectionMethod`) per class for micro performance wins. Reduce reflection overhead once per class, not per resolution.

## Autowiring Algorithm

The `ReflectionResolver` performs:

1. Cache & fetch the constructor reflection.
2. If no constructor → instantiate directly.
3. For each parameter:
	 * If parameter annotated `#[Inject(id: "service.id")]` → resolve that ID.
	 * Else if annotated `#[Inject(param: "key")]` and `param.bag` exists → fetch bag value.
	 * Else if has a class type (non-builtin) and container has that FQCN ID → resolve recursively.
	 * Else if default value available → use it.
	 * Else if nullable → `null`.
	 * Else → throw `ContainerException` (fail fast, surfaces missing wire decisions early).

Autowiring is intentionally conservative: it only resolves known IDs and does not attempt to guess implementations. You opt into aliasing for interfaces.

### Inject Attribute
`#[Inject(id: 'cache.store')]` forces a specific service. Use `param:` for lightweight parameterization (e.g., environment or feature flag values) drawn from the `ParamBag` placed under `param.bag`.

## Circular Dependency Detection

The runtime container keeps a `$resolving` map; re-entry of an ID during its own resolution triggers a `ContainerException` including the full chain: `A -> B -> C -> A`. Refactor by introducing an abstract interface boundary and lazy factory or splitting responsibilities.

## Scoped Overrides & Testing

`$container->with(['logger' => fn() => new NullLogger])` returns a new container instance whose delegate is the original. Resolution order:

1. Child singletons / definitions
2. Child delegates missing IDs to the parent (`delegate->get()`)

This pattern is ideal for overriding heavy external integrators (database, queue) in tests without mutating global definitions.

## Tagging & Ordered Collections

Providers call `$this->tag('service.id', 'tag.name', priority)`. After all providers execute, `ContainerFactory` converts each tag bucket into a `TaggedIteratorDefinition`. On resolve:

1. Entries sorted by descending priority.
2. Each service realized and collected into an array.

Use cases:
* Pipeline assembly (e.g., background warmups, plugin style voters)
* Multi-implementation aggregations
* Conditional discovery (only register services; tags supply iteration)

Because arrays are shared, all consumers get a stable reference (saves memory & ensures consistent ordering).

## Providers & Extension Loading

Core providers extend `BaseServiceProvider` and must implement `defs()`. Helpers available:

* `autowire(FQCN, shared=true)`
* `alias(aliasId, targetId)`
* `tag(serviceId, tagName, priority)`

`ContainerFactory::providers()` composes an ordered list of framework providers (e.g., `CoreProvider`, `ConsoleProvider`, `StorageProvider`, etc.), instantiates each with a shared `TagCollector`, merges their definitions, then adds extension-provided definitions.

### Extensions
Extensions discovered by `ProviderLocator::all()` can expose either:

* Static `defs()` (typed, returns full definition array)
* Static `services()` (DSL) – parsed by a `ServicesLoader` (currently `DefaultServicesLoader`) and accompanied by tag metadata

If both exist, `defs()` wins (deterministic explicit code preferred over DSL).

### Publishing Tags
Typed providers may optionally implement static `tags()` returning a map of tag name → entries. DSL specs can embed `tags` entries per service. Both feed into the same `TagCollector` pipeline.

## ParamBag & Lightweight Parameters

`ParamBag` (ID: `param.bag`) holds tiny immutable config values (like current env) that are safe to embed into compiled output and quick to access. Avoid large structured configuration here—use full config files & factories instead.

## Compilation Path

In production mode (`ContainerFactory::create(true)`):

1. Attempt to load precompiled class from `storage/cache/container/CompiledContainer.php`.
2. If absent, reflect the runtime container definitions and invoke `ContainerCompiler`.
3. Compiler emits a class implementing `Psr\Container\ContainerInterface` with:
	 * Dedicated build methods per service ID.
	 * Singleton array pre-initialized with null placeholders.
	 * Switch-based `has()` and `get()` for O(1) jump tables inside the interpreter loop.

### Supported for Compilation
* `ValueDefinition` (object export rules for known safe types)
* `AutowireDefinition` (constructor parameter compilation with inline `get()` calls)
* `TaggedIteratorDefinition` (pre-sorted sequence of `get()` calls)
* `AliasDefinition` (direct case forwarding)

### Not Supported
`FactoryDefinition` and any unknown `DefinitionInterface` subclass. The compiler aborts with a diagnostic listing unsupported IDs. To enable compilation, refactor factories into either:

* A value (precompute at build time) if deterministic & immutable
* An autowired class whose constructor performs minimal setup
* Smaller composed autowired services + a trivial value aggregator

If compilation fails, runtime container is retained—functionality unaffected, only startup micro-optimizations lost.

## Performance Characteristics

| Concern | Strategy |
| ------- | -------- |
| Reflection Cost | Single cached `ReflectionResolver` instance; compilation replaces runtime reflection entirely. |
| Lookup Speed | Array hash lookups + early singleton return; compiled mode uses switch dispatch. |
| Memory | Shared instances reduce duplication; alias indirection negligible. |
| Warmup | Tag `lazy.background` instructs future warmup routines (hook TBD) to pre-resolve heavy services. |
| Overrides | Child container layering avoids copying entire definition maps. |

## Extension Points

| Area | How to Extend | Notes |
| ---- | ------------- | ----- |
| New Service | Add to custom provider `defs()` or extension DSL | Prefer autowire for pure object graphs. |
| Replace Core Implementation | Register alias FQCN → custom class or override ID via child container | Ensure interface parity. |
| Add Cross-Cutting Service | Tag into existing collection (e.g., `cache.pool`) | Priority to control ordering. |
| Parameter Injection | Add keys to `ParamBag` or create dedicated config service | Keep ParamBag lean. |
| Compilation Behavior | Contribute only supported definitions | Future roadmap may broaden support. |

## Recommended Practices

1. Prefer `AutowireDefinition` unless you need conditional logic or side-effects.
2. Use aliases to bind interfaces to concrete classes; keep the FQCN of the implementation resolvable directly if practical.
3. Keep factories idempotent & fast; move heavy IO (network/schema introspection) behind lazy methods invoked later.
4. Avoid injecting the container itself (service locator anti-pattern). Accept dependencies explicitly.
5. Collapse deeply nested constructors by introducing cohesive intermediate services.
6. Tag services for aggregation rather than manually building arrays in factories—improves compilation and ordering consistency.
7. Convert factories to autowired classes to enable compilation in prod.
8. Fail fast: let missing dependencies surface as `ContainerException` early in development.

## Common Anti‑Patterns

| Anti-Pattern | Why It Hurts | Better Approach |
| ------------ | ----------- | --------------- |
| Container-as-service-locator inside business code | Hides dependencies, complicates testing | Explicit constructor injection / `#[Inject]` overrides. |
| Storing mutable runtime state in `ValueDefinition` | Breaks invariants if mutated after share | Use a dedicated stateful service class. |
| Giant multi-purpose factory closures | Hard to test, not compilable | Split into small autowired services. |
| Overusing `param.bag` for complex config graphs | Bloats compiled output, obscures source of truth | Load structured config via factories. |
| Abusing priorities for logic ordering | Implicit, brittle coupling | Model explicit pipeline or chain of responsibility. |

## When to Use a Factory vs Autowire

Choose a factory if:
* Construction depends on runtime environment branching (e.g., choose driver by config)
* You must catch and downgrade exceptions (return Null implementation)
* You need to seed a singleton with dynamic data not expressible as constructor args

Otherwise, create a dedicated class and register via `autowire()`.

## Minimal Examples

### Autowired Service
```php
final class Slugifier {
		public function __construct(private \Psr\Log\LoggerInterface $logger) {}
		public function slug(string $title): string { /* ... */ }
}

// Provider
$defs[Slugifier::class] = $this->autowire(Slugifier::class);
```

### Interface Binding via Alias
```php
$defs[CacheInterface::class] = $this->alias(CacheInterface::class, InMemoryCache::class);
$defs[InMemoryCache::class] = $this->autowire(InMemoryCache::class);
```

### Parameter Injection
```php
final class Greeter {
	public function __construct(#[Inject(param: 'env')] private string $env) {}
}
```

### Explicit Override in a Test
```php
$testContainer = $container->with([
	'logger' => fn() => new Psr\Log\NullLogger(),
]);
```

## Summary

Glueful's container favors explicit, analyzable definitions with a small surface area of behaviors, enabling straightforward optimization (compilation) and safe extension (providers + tags). By leaning on autowiring and alias indirection—and restricting factory usage—you gain fast startup, predictable dependency graphs, and maintainable service architecture.
