# Performance Principles

Performance is treated as a first‑class product feature: predictable tail latency (p95/p99) > raw mean throughput. This doctrine consolidates existing mechanisms (caching, rate limiting, context optimization) and provides a rubric for evaluating new contributions.

---

## 1. Goals

| Goal | Description |
|------|-------------|
| Predictable latency | Keep p95 & p99 stable under typical burst, multi-tenant load |
| Linear scalability | Horizontal scale adds capacity with near-linear efficiency |
| Efficient protection | Guardrails (rate limits, idempotency) add microseconds, not milliseconds |
| Fast cold start | Minimize first-request penalty after deploy / scale-out |
| Data locality | Reduce serialization & redundant transformation steps |
| Measurable budgets | Each layer owns a latency & allocation budget |

Non-goals: Premature micro-optimizing PHP engine internals, hand-writing extensions before profiling, sacrificing clarity for speculative nanoseconds.

---

## 2. Core Principles

1. Amortize expensive work (compile container, pre-warm caches, reuse connections).
2. Short-circuit early (auth failures, permission denies, malformed payload) to free resources.
3. Avoid needless copies—operate on streams / iterators where feasible.
4. Cache results only if (hit_ratio * miss_cost) justifies complexity & invalidation risk.
5. Protect tail latency: design features for constant-time or sub-linear growth relative to tenants/data size.
6. Instrument before optimizing: changes must show delta in metrics (latency histogram / allocation counters).
7. Degrade gracefully (shed optional work) rather than allow cascading slowdowns.
8. Keep hot path branching minimal & predictable; push complexity to cold/async paths.
9. Reuse strategy objects & service singletons via the container (avoid per-request re-instantiation).
10. Eliminate hidden N+1 patterns (DB, permission checks, cache fetch loops) early.

## 4. Cost Model (Mental Accounting)

| Operation | Typical Cost (qualitative) | Optimization Levers |
|-----------|---------------------------|--------------------|
| Container resolution (singleton) | O(1) negligible post-compile | Pre-compile, avoid dynamic reflection per call |
| Cache get / set (Redis) | ~sub-ms network RTT | Batch, tag invalidation grouping |
| Rate limiter attempt | O(log n) sorted set | Key pruning, reuse pipeline, minimize per-attempt allocations |
| Permission evaluation | Voter chain length dependent | Short-circuit ordering, cache stable decisions, consolidate queries |
| DB query (read) | ms to 10s ms | Index coverage, query cache tagging, projection reduction |
| External HTTP call | 10s–100s ms | Circuit breaker, timeout tuning, response caching |
| JSON encode large payload | CPU bound (size linear) | Stream / partial encode, compress later layers |

Budget heuristic: If a layer regularly exceeds 10–15% of total request time, profile and consider mitigation.

## 5. Key Mechanisms & Patterns

### 5.1 Container & Object Lifecycle
* Favor singleton services for stateless strategies.
* Pre-resolve heavy dependencies during bootstrap to front-load cost when safe.
* Use factory definitions only where runtime parameters vary meaningfully.

### 5.2 Caching Discipline
* Response cache keys incorporate permission & varying headers to avoid over-broad hits.
* Query caching restricted to safe SELECTs; hashed normalized SQL + tags enable coherent invalidation.
* Permission decision cache bounded by TTL + role/scope context to avoid stale privilege retention.

### 5.3 Rate Limiter Efficiency
* Sliding window deletes expired timestamps before cardinality check (keeps structure small).
* Burst + sustained split reduces worst-case memory/time over naive token bucket resets.
* Adaptive behavior gating prevents wasted downstream work on abusive traffic.

### 5.4 Error Path Optimization
* Lightweight context path avoids re-collecting heavy request metadata for frequent minor errors.
* Sanitization only runs for messages leaving trust boundary.

### 5.5 Async & Deferral
* Move non-critical enrichments (analytics, secondary lookups) to background queues when p95 threatened.
* Batch metrics flush (threshold-based) reduces sync overhead.

### 5.6 Data Access Minimization
* Retrieve only needed columns; compose aggregates upstream rather than N queries.
* Collocate permission & ownership checks with primary fetch to prevent N+1.

### 5.7 Tail Latency Protection
* Circuit-break or fast-fail external clients after short timeout ceiling; fallback cached stale data if permissible.
* Use multi-level rate limits to prevent resident abusive patterns from shaping tail distribution.

## 6. Measurement & Budgets

| Layer | Primary Metrics | Example Budget |
|-------|-----------------|----------------|
| Request total | p50 / p95 / p99 latency | < 50ms p95 (internal API baseline) |
| Rate limiting | Attempt latency | < 1ms average |
| Permission evaluation | Decision latency | < 3ms average / < 10ms p95 |
| Query cache | Hit ratio | > 70% for tagged hot queries |
| Response cache | Hit ratio (eligible endpoints) | > 80% for asset-like endpoints |
| Exception handler | Overhead per error | < 2ms additional |
| Metrics batching | Flush interval | 1–5s or 50 records |

Budgets are guidance; treat variance + trend lines as more actionable than single spikes.

Instrumentation recommendations:
* Add histogram timers around permission evaluation & external calls.
* Emit counter: rate limit rejections per action per minute.
* Track queue depth / worker utilization for backpressure feedback.

## 7. Optimization Playbook

| Symptom | Investigation | Typical Fix |
|---------|---------------|-------------|
| Rising p99, stable p50 | Long-tail external or DB outliers | Add timeout / caching / bulk fetch |
| Elevated CPU | Excess serialization / JSON work | Stream responses, reduce payload size |
| Cache thrash | Low hit ratio, high churn | Adjust key granularity, increase TTL, review invalidation triggers |
| Rate limit false positives | Legit users throttled | Tune burst window or introduce conditional user tiers |
| Memory climb | Large context objects retained | Prune caches, reduce context verbosity, check object graphs |
| Slow error storms | Heavy logging & context gathering | Lightweight context path & sample logs |
| DB connection saturation | High concurrent blocking | Add query batching, raise pool, offload read replicas |
| External timeout cascading | Retries amplify latency | Implement exponential backoff + circuit breaker |

Decision workflow:
1. Confirm budget violation with metrics.
2. Reproduce locally or in staging with targeted load.
3. Profile (sampling + flame graph) to locate hotspots.
4. Apply smallest fix meeting budget.
5. Re-measure; rollback if regression elsewhere.

## 8. Extension Guidelines

| Contribution Type | Guidance |
|-------------------|----------|
| New middleware | Keep constant time; avoid I/O; put heavy logic behind feature flag |
| New caching layer | Define invalidation narrative before merging | 
| New external integration | Predefine timeout, retries, circuit policy |
| New background worker | Register metrics for queue depth & processing rate |
| New permission voter | Order by probability of early exit; ensure pure & deterministic |
| New rate rule | Document expected effect & rollback condition |

---

## 9. Anti‑Patterns

| Anti-Pattern | Impact | Better Approach |
|-------------|--------|-----------------|
| Cache everywhere first | Invalidation complexity, stale bugs | Profile then cache hot paths |
| Logging full objects | Memory & I/O bloat | Log IDs + minimal facets |
| Wide try/catch swallowing | Hides slow fail paths | Narrow scope + measure errors |
| Per-request constructing heavy clients | Repeated setup overhead | Container singletons / pools |
| Blindly increasing concurrency | Amplifies contention | Measure saturation & queue depth |
| Mutation inside permission voters | Unpredictable side-effects | Pure, idempotent voters |
| Large synchronous exports | Blocks workers & memory spike | Stream or async export job |

---

## 10. Regression Guarding & Testing

Recommended automated checks:
* Synthetic load test (nightly) capturing p95 deltas vs baseline.
* Unit test for rate limiter ensures O(1)/log behavior remains (no inadvertent O(n²) loops).
* Benchmark harness for permission evaluation complexity as voters added.
* Cache hit ratio monitoring dashboard with alert when sharp sustained drop > X%.
* Error handler overhead micro-benchmark (simulate 1k validation errors) verifying context tiering holds.

Release checklist additions:
1. New external dependency has timeouts + circuit strategy.
2. New caches documented in Caching Strategies doc with invalidation path.
3. High-churn code paths avoid per-request regex in hot path.
4. Added metrics namespaced & cardinality reviewed.

## 12. Quick Reference

| Concern | Principle / Location | Action |
|---------|---------------------|--------|
| High p99 | Optimize tail not mean | Add timeouts, reduce fan-out |
| Slow errors | Lightweight context path | Keep verbose off for hot exceptions |
| External IO | Circuit & timeout policy | Cache success/failure when safe |
| Permission chain | Order by cheap deny first | Add per-voter metrics (roadmap) |
| Caching decision | Miss_cost * expected_hits > overhead | Else skip caching |
| Rate limiter cost | Sliding window O(log n) | Avoid large inactive windows |
| Logging volume | Structured minimal context | Sample noisy channels |
