# Error Handling & Exceptions

Predictable error boundaries, minimized leakage, rich observability context, and a single normalization pipeline. This concept explains how the framework classifies, logs, sanitizes, rate‑limits, and serializes failures from domain logic to final HTTP error payloads.

---

## 1. Goals & Non‑Goals

| Goal | Description |
|------|-------------|
| Uniform envelope | All exceptions resolved to a stable JSON error structure via `ExceptionHandler::handleException()` -> `Response::error()` |
| Least privilege disclosure | Hide implementation details (file paths, SQL, secrets) outside debug/local contexts (`sanitizeErrorMessage()`) |
| Contextual logging | Attach request, user, environment context (optimized for frequency) without risking recursive failures |
| Categorized channels | Map exception types to semantic log channels for routing & alert policies |
| Rate pressure safety | Throttle per‑IP error response frequency to mitigate amplification / abuse |
| Extensible taxonomy | Simple path to add new domain exceptions & integrate into pipeline |
| Deterministic status mapping | Clear table translating exception classes → HTTP status codes |

Non‑Goals: Full RFC 9457 Problem Details parity (we adopt a pragmatic subset), IDE style stack browsing in responses, automatic retry orchestration (handled by clients / queues).

---

## 2. Design Principles

1. Fast fail classification (specific → generic) keeps branching predictable.
2. Sanitization occurs only once at the edge; internal layers see raw messages.
3. Missing context never blocks error emission (defensive try/catch around event + logger usage).
4. High‑frequency low‑severity errors use lightweight context to reduce allocation & log volume.
5. Observability correlation (request_id, user_uuid) is always present (generated if absent).
6. Strict environment gate for verbose details: `app.debug && (APP_ENV in [development, local])`.
7. Enum‑like exception classes separate semantics (Auth vs Permission vs RateLimit) enabling targeted automation later (metrics, notifications).

## 3. Exception Taxonomy

Core exception families (location: `src/Exceptions/` unless noted):

| Category | Class | Purpose | Typical Trigger | HTTP Status |
|----------|-------|---------|-----------------|-------------|
| Validation | `ValidationException` | Field or structural validation failure | Input DTO / request parsing | 422 |
| Authentication | `AuthenticationException` | Identity could not be established | Missing/invalid credentials | 401 |
| Authorization | `\Glueful\Permissions\Exceptions\UnauthorizedException` | Authenticated but not permitted | Gate / voter denies | 403 |
| Permission System | `PermissionException` | Internal permission evaluation failure | Provider misconfig / context error | 403 (sanitized) |
| Not Found | `NotFoundException` | Resource absence | Repository / lookup miss | 404 |
| Rate Limiting | `RateLimitExceededException` | Policy threshold exceeded | Middleware / guard | 429 |
| Security | `SecurityException` | Security rule violation (e.g. signature) | Integrity / CSRF / tamper detection | custom (often 400/401/403) |
| Protocol | `HttpProtocolException` | Malformed HTTP semantics | Header / method constraints | 400/422 |
| HTTP Client | `HttpException` / `HttpClientException` | Downstream call failed | Transport / 5xx / timeout | surfaces upstream code |
| Business Logic | `BusinessLogicException` | Domain invariant breach | Service layer rule conflict | 409/422 (varies) |
| Extension | `ExtensionException` | Extension boundary failure | Extension runtime error | derived from exception |
| Database | `DatabaseException` | Persistence failure | Query / transaction error | 500 (sanitized) |
| Cache | `CacheException` | Cache layer failure | Backend unreachable | 500 (fallback path) |
| Generic API | `ApiException` | Structured error with status + data | Service surfaces user‑safe payload | provided |
| Permission Provider Missing | `ProviderNotFoundException` | Configured permission provider absent | Boot / provider registry | 500 |
| Fallback | Any other `\Throwable` | Unexpected defect | Programming error | 500 |

Ordering matters during classification: specific subclasses are matched first, generic fallback last.

## 4. Normalization Flow

1. Global registration (`ExceptionHandler::register()`) installs three handlers:
	 - `set_exception_handler` → `handleException()`
	 - `set_error_handler` converts PHP errors to `ErrorException`
	 - `register_shutdown_function` converts fatal errors into synthetic exceptions
2. Incoming exception enters classification ladder (see Taxonomy) to assign status + message + optional data.
3. Context building: `getOptimizedContext()` chooses lightweight vs verbose; may use cached snapshot for performance (<30s reuse window).
4. Sanitization: If not in debug/local, `sanitizeErrorMessage()` redacts file paths, DB details, sensitive tokens, long traces.
5. Logging: `logError()` maps to channel (e.g. `validation`, `auth`, `ratelimit`, `permissions`). Channel written as context key; logger chosen via container (PSR‑3).
6. Event emission: `ExceptionEvent` dispatched (non-blocking; failures swallowed) enabling side-effects (metrics enrichment, alert hooks) without coupling.
7. Rate limiting: If IP exceeded error budget (default 60/min), short-circuit with generic 429 (no classification or logging details) to prevent log storm.
8. Serialization: `outputJsonResponse()` delegates to `Response::error()` to enforce envelope contract.

Sequence can be visualized (simplified):

```
Throwable -> (RateLimit Gate) -> (Classification) -> (Context Builder) -> (Sanitize) -> (Log + Event) -> (Envelope Serialize) -> JSON
```

## 5. Mapping & Status Codes

| Class | Status | Envelope message strategy | Data field |
|-------|--------|---------------------------|-----------|
| ValidationException | 422 | Use exception message | `errors` map from exception |
| AuthenticationException | 401 | Exception message | null |
| UnauthorizedException | 403 | Exception message | null |
| PermissionException | 403 | Fixed: "Permission denied" | optional context (debug only) |
| NotFoundException | 404 | Exception message | null |
| RateLimitExceededException | 429 | Exception message | `{ retry_after }` |
| SecurityException | custom | Exception message | null |
| HttpException / HttpClientException | custom | Exception message | upstream `data` |
| DatabaseException | 500 | "Database operation failed" (or sanitized) | optional sanitized error |
| ExtensionException | custom | Exception message | extension `data` |
| ApiException | custom | Exception message | custom `data` |
| ErrorException | 500 | "System error occurred" | optional file,line (debug) |
| Other Throwable | 500 | "Unexpected error occurred" | type + sanitized error (debug) |

## 6. Response Envelope

Framework standard error JSON produced by `Response::error()` (adapted to existing success shape):

```jsonc
{
	"success": false,
	"message": "Permission denied",
	"code": 403,
	"data": { "retry_after": 42 } // optional
}
```

Key points:
* Deterministic keys allow client schema generation.
* `code` duplicates HTTP status for easier JS fetch layer decoding (body-only inspection).
* `data` omission avoids null noise; only present when semantic payload exists.
* Validation errors typically supply structure: `{ field_errors: { email: ["invalid"] } }` (implementation-specific).

While not full RFC 9457, mapping is close enough for automated adaptation if needed later.

## 7. Context Building & Sanitization

Strategies implemented in `ExceptionHandler`:

| Mechanism | Purpose | Detail |
|-----------|---------|--------|
| Verbose vs Lightweight | Performance tiering | High-frequency (Validation, NotFound) skip heavy system/env fields |
| Context caching | Reduce duplicate computation | Reuses context for same user within 30s window |
| Header filtering | Privacy | Sensitive headers replaced with `redacted` |
| Body metadata only | Security | Size + presence recorded; body content not logged |
| Sanitization regex | Leak prevention | File paths, DB creds, stack frames, tokens removed unless debug |
| Message collapsing | Noise reduction | Long/technical messages collapsed to generic phrase |
| Memory & timing metrics | Diagnostics | Basic perf signals included without separate metric instrumentation |

Lightweight context still includes correlation (`request_id`, `user_uuid`) ensuring joinability with metrics/traces (see Observability Model).

## 8. Rate Limiting of Error Responses

`checkErrorRateLimit()` stores per-IP timestamps in-memory, enforcing a sliding 1‑minute window (default max 60). Exceeding the limit bypasses logging & classification returning a generic 429 with minimal body to avoid: amplification, log cost spikes, PII extraction attempts. This is complementary to request level rate limits (documented in lifecycle & controller traits) and specifically guards failure surfacing.

Future improvements (see Roadmap) may externalize counters (Redis) for multi-instance support.

---

## 9. Logging & Observability Integration

Integration points:
* Structured logging: Each error carries channel and contextual keys enabling targeted sinks or alert thresholds.
* Metrics correlation: The `request_id` present here can match latency metrics and (future) per-exception counters.
* Tracing: Although exceptions are not automatically converted into spans, the generated `request_id` can be bridged to tracing middleware. Roadmap includes span status enrichment on unhandled errors.
* Event dispatch (`ExceptionEvent`): decoupled mechanism for metrics, anomaly detection, or real-time notifications (e.g., Slack) without modifying handler core.

## 10. Extension Points

| Extension Need | Mechanism | Example |
|----------------|-----------|---------|
| New domain error class | Create exception extending `ApiException` or domain base; throw in service | `class PaymentDeclinedException extends ApiException` |
| Custom status mapping | Insert conditional before fallback in `handleException()` | Map `PaymentDeclinedException` → 402 |
| Channel routing | Add class => channel in `$channelMap` | `PaymentDeclinedException` → `billing` |
| Structured payload | Use `ApiException` / `ExtensionException` data bag | `new ApiException('Invalid state', 409, ['state' => 'archived'])` |
| Observability side effects | Listen for `ExceptionEvent` | Listener increments counter or emits trace annotation |
| Redaction policy change | Override / wrap `sanitizeErrorMessage()` via composition & PR | Add custom scrub patterns |
| Multi-instance rate limit | Replace storage in `checkErrorRateLimit()` | Redis / centralized leaky bucket |

## 11. Anti‑Patterns

| Anti‑Pattern | Why Harmful | Preferred Approach |
|-------------|-------------|--------------------|
| Throwing generic `\Exception` for domain conditions | Loses semantics & channel mapping | Create specific exception type |
| Returning error arrays instead of throwing | Bypasses normalization & logging | Throw appropriate exception |
| Embedding PII in messages | Risk of leakage even after sanitization | Put sensitive data in structured secure storage, reference ID only |
| Logging raw request body | Potential secrets & large payloads | Rely on body size metadata only |
| Catch + rethrow as different status without cause chain | Drops original context | Wrap while preserving previous (`new ApiException(..., previous: $e)`) |
| Overusing 500 for user errors | Blurs alert signals | Choose 4xx reflective of client fault |

## 12. Testing Strategies

`ExceptionHandler::setTestMode(true)` prevents `exit` and captures the last response (`getTestResponse()`). Use this to assert: status mapping, sanitization in non-debug environment, inclusion/exclusion of `data`.

Suggested test cases:
1. Validation path: Throw `ValidationException` => 422 with errors array, lightweight context used (assert absence of heavy keys if exposing log context stub).
2. Sanitization: Force `DatabaseException` with connection string; ensure message collapsed when debug=false.
3. Rate limit: Loop >60 simulated exceptions from same IP; final response is generic 429 without detailed logging side effects.
4. Permission denial: `UnauthorizedException` vs `PermissionException` differences (message vs standardized + optional context hidden).
5. Fallback: Unknown custom exception → 500 "Unexpected error occurred".

| Item | Rationale |
|------|-----------|
| RFC 9457 adapter | Optional Problem Details shape for ecosystem compatibility |

| Automatic retry hint field | Provide `retryable: boolean` in envelope for idempotent safe operations |

## 16. Example: Adding a Domain Exception

```php
class PaymentDeclinedException extends ApiException {
		public function __construct(string $reason) {
				parent::__construct('Payment declined', 402, ['reason' => $reason]);
		}
}

// Throw in service
if ($gateway->declined()) {
		throw new PaymentDeclinedException($gateway->reason());
}

// Optional: add to channel map for routing (e.g., billing alerts)
// self::$channelMap[PaymentDeclinedException::class] = 'billing';
```

Resulting JSON (non-debug):

```jsonc
{
	"success": false,
	"message": "Payment declined",
	"code": 402,
	"data": { "reason": "insufficient_funds" }
}
```
