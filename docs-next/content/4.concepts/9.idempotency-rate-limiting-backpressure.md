# Idempotency, Rate Limiting & Backpressure

Unified safeguards for correctness (idempotency), fairness (rate limiting), and resilience (backpressure). This concept ties together existing rate limiting primitives (`RateLimiter`, `AdaptiveRateLimiter`, `RateLimitingTrait`, distributed coordinator) with recommended idempotency patterns and queue pressure controls.

---

## 1. Goals

| Goal | Description |
|------|-------------|
| Prevent duplicate side‑effects | Ensure retried client operations don't create extra writes/charges |
| Fair resource allocation | Per user/IP/action limits to isolate abusive or bursty actors |
| Adaptive defense | Behavior scoring & rules reduce manual threshold tuning |
| Multi-level protection | Combine short & long windows (burst + sustained) |
| Graceful degradation | Shed optional work / slow intake instead of failing catastrophically |
| Horizontal scalability | Distributed coordination for limits across nodes |
| Observability linkage | Emit consistent identifiers to correlate throttling & errors |

Non‑goals: Payment-level two‑phase commit, full consensus locking, perfect duplicate suppression for all conceivable races.

---

## 2. Design Principles

1. Idempotency is explicit: clients supply a stable key for operations that may retry.
2. Rate limiting before expensive work (auth/context/costly DB) when safe.
3. Adaptive logic augments static limits—never replaces a deterministic floor.
4. Backpressure favors queue deferral over synchronous rejection where semantics allow.
5. Observability first: every throttle or suppression event is loggable with reason + key.
6. Cheap path for allowed requests (constant time sorted set ops, minimal allocations).
7. Configuration centralization: environment toggles & thresholds in `security.rate_limiter.*`.

## 4. Idempotency Patterns (Recommended)

The codebase does not yet ship a dedicated Idempotency service; adopt these patterns now, anticipating a future `IdempotencyStore` abstraction.

| Pattern | Use Case | Implementation Sketch | Expiry |
|---------|----------|-----------------------|--------|
| Cache Key + Stored Result | POST create with client retries | Cache `idem:{key}` => serialized success payload + status; on duplicate return stored | 24h (configurable) |
| Hash of Mutating Input | Bulk operations without client key | Derive key from stable JSON canonicalization of request body | 1–6h |
| DB Natural Constraint | Create-if-not-exists semantics | Rely on unique constraint; catch duplicate, load existing | Constraint lifetime |
| Saga Step Idempotency | Multi-step workflows | Store step completion marker keyed by saga + step | Saga TTL |
| Outbox / Dedup Table | External side-effects (emails, payments) | Insert with unique idempotency key; ignore duplicate conflict | Business TTL |

Guidelines:
* Generate 409 or 200 (not 201 repeatedly) on duplicate depending on semantics.
* Always return original response shape for cached duplicates.
* Distinguish unsafe vs idempotent endpoints in API docs (e.g., `POST /charges` idempotent when key provided).

Minimal example (future utility):

```php
$key = $request->headers->get('Idempotency-Key');
if ($key) {
	$cacheKey = 'idem:' . sha1($key . ':' . $request->getRequestUri());
	if ($cached = $cache->get($cacheKey)) {
		return Response::fromArray($cached); // previously serialized envelope
	}
}

// perform write
$response = Response::success(['id' => $entity->id], 'Created');

if (isset($cacheKey)) {
	$cache->set($cacheKey, $response->toArray(), 86400);
}
```

## 5. Rate Limiting Strategies (Implemented)

Grounded in `RateLimitingTrait` & supporting classes:

| Strategy | Method | Purpose | Notes |
|----------|--------|---------|-------|
| Direct Sliding Window | `rateLimit()` | Core per-action limit | Key format: `Class:action:subject` |
| Method Auto Detection | `rateLimitMethod()` | Convenience by controller method | Falls back to HTTP method config |
| Resource Operation | `rateLimitResource()` | Differentiate read/write/bulk/export | Pulls `security.rate_limits.operations.*` |
| Multi-Level | `multiLevelRateLimit()` | Minute/hour/day cascading | Disables adaptive inside loop |
| Conditional User Type | `conditionalRateLimit()` | Role/anon based fairness | Accepts override map |
| Adaptive Behavior | `rateLimit(... useAdaptive)` | Suspicious pattern suppression | Behavior score > 0.8 → early 429 |
| Burst + Sustained | `burstRateLimit()` | Allow quick spikes while protecting average | Two separate keys (10s vs full window) |
| Headers Exposure | `getRateLimitHeaders()` / `withRateLimitHeaders()` | Communicate budget to clients | X-RateLimit-* standard style |
| Reset Capability | `resetRateLimits()` | Admin operational override | Requires `system.rate_limits.reset` permission |
| Behavior Gating | `requireLowRiskBehavior()` | Sensitive op gating via behavior score | Throws `SecurityException` |

### Internals

`RateLimiter` implements a sliding window using sorted set semantics (`zadd`, `zrange`, `zremrangebyscore`, `zcard`) exposed through `CacheStore`. Each attempt prunes expired entries then tests cardinality; complexity is O(log n) on a Redis backend. `getRetryAfter()` returns time until earliest entry exits the window enabling precise `retry_after` values in exceptions.

`RateLimiterDistributor` coordinates cluster nodes: node registration, global limit snapshots, stale cleanup, and (if Redis available) pub/sub updates. It also uses lightweight lock prefixes for race avoidance (future: formal distributed lock service).

`RateLimiterRule` defines dynamic adaptive rules (maxAttempts, windowSeconds, threshold, conditions) enabling runtime adjustments without code deployment.

## 6. Backpressure & Load Shedding

Backpressure surfaces when upstream demand > sustainable processing. Current codebase signals & tools:

| Mechanism | Source | Role |
|-----------|--------|------|
| Queue Auto Scaling | `queue:autoscale` command (AutoScaler, ResourceMonitor, ScheduledScaler) | Adds workers when backlog or resource metrics warrant |
| Scheduled Scaling | `ScheduledScaler` | Predictive capacity alignment (time-of-day / campaigns) |
| Resource Monitoring | `ResourceMonitor` | CPU/memory insights feeding scaling heuristics |
| Streaming Monitor | `StreamingMonitor` | Real-time feedback loop for ops tuning |
| Rate Limit Tightening | (Planned) dynamic rule updates | Lower thresholds under persistent saturation |
| Write Deferral | (Planned) enqueue non-critical synchronous work | Convert expensive sync endpoints to asynchronous workflows |
| Graceful Degradation | Manual flags | Skip optional enrichments (e.g., secondary lookups) |

Recommended enhancement path:
1. Introduce a `BackpressureController` metric (queue depth / worker count ratio) exported to metrics system.
2. Feedback loop: when ratio > threshold, push temporary lower `maxAttempts` via adaptive rules.
3. Provide 503 or 429 with `retry_after` for clearly saturated endpoints (prefer 429 if policy-based, 503 if systemic).
4. Instrument decision latency to ensure protections don’t dominate critical path.

## 7. Interactions Matrix

| Scenario | Idempotency | Rate Limiting | Backpressure |
|----------|-------------|---------------|--------------|
| Client retry after timeout | Prevent duplicate effect | Window unchanged (same key not bypass) | Not directly triggered |
| Script burst (100 rapid POSTs) | Keys stable → 1 effect | Burst limiter engages; sustained halts | Scaling may add workers if queued |
| Malicious credential stuffing | Not relevant | Adaptive behavior score → early 429 | None (synchronous throttle) |
| Heavy ingest causing queue backlog | Outbox dedups downstream events | Rate limits may slow producers | Auto-scaler adds workers; potential shedding |
| Payment creation race | Idempotency key ensures single charge | Rate limiting slows brute force | Backpressure may defer to queue |

## 9. Anti‑Patterns

| Anti-Pattern | Why Harmful | Better |
|-------------|-------------|-------|
| Rely solely on client not retrying | Network ambiguity guarantees retries | Provide idempotency key contract |
| Using 500 for throttles | Misleads monitoring & clients | Use 429 (policy) or 503 (system saturation) |
| Storing full responses without TTL | Memory bloat | Apply bounded TTL (24h) and size guard |
| Counting attempts in SQL row | Contention & lock amplification | Use cache/Redis sorted sets |
| Overly low static limits | False positives under normal bursts | Layer burst + sustained + adaptive |
| Always rejecting under load | Wastes partial work | Provide deferral (enqueue) where semantics permit |
| Silent shedding | Hard to debug client behavior | Emit structured log + metric counter |

## 10. Testing Strategies

| Test | Focus | Assertion |
|------|-------|-----------|
| Idempotent POST duplicate | Cache replay | Second response identical, no second side effect |
| Sliding window boundary | Edge expiry | Attempt passes exactly when oldest timestamp exits window |
| Burst then sustained | Burst limiter path | Initial > burstSize triggers sustained window evaluation |
| Adaptive behavior high score | Behavior gating | Score > threshold returns 429 alt message |
| Multi-level cascade | Long activity | Exceed hour limit while minute resets still blocks |
| Distributed synchronization | Multi-node simulation | Consistent total attempts across nodes |
| Queue saturation feedback | Backpressure integration (future) | Temporary lower limits applied |
