# Controller Patterns & BaseController

Glueful controllers are intentionally thin orchestration layers. They:

- Validate & normalize inbound request data
- Delegate business logic to services / repositories
- Enforce authentication, authorization, rate limiting, ownership & field-level visibility
- Apply caching & conditional request semantics (ETag / Last-Modified)
- Shape & serialize response data (groups / meta)

Every first‑party controller extends `BaseController`, which composes narrowly scoped traits instead of a monolithic superclass. This keeps responsibilities explicit and promotes selective extension without inheritance depth.

## Composition Model

`BaseController` pulls in these traits (plus a DB helper):

| Trait | Responsibility | Key Methods (non‑exhaustive) |
|-------|----------------|------------------------------|
| `CachedUserContextTrait` | Request‑scoped auth context & permission caching | `getCachedUser()`, `isCachedAuthenticated()`, `hasCachedPermission()`, `requireCachedAuthentication()`, `refreshUserContext()` |
| `AuthorizationTrait` | Higher‑level permission gates & convenience | `can()`, `requirePermission()`, `canAny()`, `isAdmin()` |
| `RateLimitingTrait` | Multi‑mode rate limiting & adaptive behavior | `rateLimit()`, `rateLimitMethod()`, `rateLimitResource()`, `multiLevelRateLimit()`, `conditionalRateLimit()`, `burstRateLimit()`, `requireLowRiskBehavior()` |
| `ResponseCachingTrait` | Response/query/fragment caching + ETag helpers | `cacheResponse()`, `cacheQuery()`, `cachePaginatedResponse()`, `cacheByPermission()`, `cacheFragment()`, `invalidateResourceCache()` |
| `FieldLevelPermissionsTrait` (opt‑in) | Field redaction based on per-field permissions | `applyFieldPermissions()`, `getSensitiveFields()` |
| `DatabaseConnectionTrait` | Low‑level DB connection helpers | (internal convenience methods) |

You can layer *more* traits in your own base class, but keep each trait single‑purpose.

## Dependency Acquisition Strategy

Controllers prefer **constructor injection** via the service container. The framework still provides guarded fallbacks to avoid brittleness during early bootstrap:

1. Attempt injected arguments (autowired by container)
2. Fallback to static factories (e.g. `AuthBootstrap::getManager()`)
3. Resolve late via `container()->get()` for things like `Request`

This hybrid approach keeps controllers testable while tolerating minimal wiring in prototypes / skeleton applications.

### What NOT to do
Avoid ad‑hoc `new Service()` inside controller methods—prefer asking the container or a factory. This preserves swap‑ability & test isolation.

## Request Lifecycle Integration

Within the [Request Lifecycle](./1.request-lifecycle.md):
1. Global / route middleware establish security context (auth, metrics, tracing)
2. Router resolves controller & method (optionally via resource routing)
3. Controller executes method; traits consult cached context instead of repeating I/O
4. Response serialization & caching helpers finalize payload

This minimizes repeated DB/permission lookups while maintaining strict boundaries.

## Response Construction Patterns

`BaseController` supplies consistent helpers:

- `success()`, `created()`, `notFound()`, `unauthorized()`, `forbidden()`, `serverError()`
- Serialization variants: `serializeResponse()`, `serializeCreated()`, `serializeWithMeta()` for paginated or annotated datasets.
- HTTP caching variants: `cachedSuccess()`, `publicSuccess()`, `publicCached()`, `privateCached()`, `withLastModified()` & conditional negotiation via `checkNotModified()`.

### Serialization Groups
Use them to expose different *projections* of the same domain object. Example:

```php
return $this->serializeResponse($user, $this->isAdmin() ? ['admin', 'profile'] : ['public']);
```

Groups flow into `SerializationContext` ensuring separation of internal vs public fields without duplicating DTOs prematurely.

## Validation Strategy

`validateRequest()` offers a lightweight internal rule parser—good for simple endpoints or bootstrap phases.

Supported rules (current): `required`, `email`, `max:N`.

Pattern:
```php
$data = $this->getRequestData();
if ($error = $this->validateRequest($data, ['email' => 'required|email', 'name' => 'required|max:100'])) {
    return $error; // 422
}
```

For complex conditional logic, cross‑field rules, i18n messages, or advanced formats, escalate to a dedicated validation service or library—do not bloat the base helper.

## Authorization & Permission Patterns

Fast path checks:
```php
if (!$this->can('system.metrics.view')) {
    return $this->forbidden();
}
```

Strict enforcement:
```php
$this->requirePermission('resource.users.update', 'users', ['target' => $userId]);
```

Multiple candidate permissions (OR):
```php
if (!$this->canAny(['resource.reports.read', 'resource.analytics.read'])) {
    return $this->forbidden();
}
```

All permission checks flow through a cached request context → minimal duplication, consistent audit data.

### Field-Level Permissions
When `FieldLevelPermissionsTrait` is enabled, the controller post‑filters records or paginated payloads, removing sensitive attributes unless the caller holds the explicit `resource.{table}.{operation}.{field}` permission. Apply it after repository hydration but before final serialization groups for deterministic shape.

## Rate Limiting Modes

| Mode | When to Use | Example |
|------|-------------|---------|
| `rateLimit()` | Generic action gating | `rateLimit("export-users", 5, 300)` |
| `rateLimitMethod()` | Per-controller-method defaults | `rateLimitMethod()` at top of method |
| `rateLimitResource()` | CRUD / bulk / export operations | `rateLimitResource('users','read')` |
| `multiLevelRateLimit()` | Burst vs sustained | `multiLevelRateLimit('password-reset')` |
| `conditionalRateLimit()` | User tier differentiation | `conditionalRateLimit('search')` |
| `burstRateLimit()` | Short bursts allowed then steady window | `burstRateLimit('ingest', 20, 200)` |
| `requireLowRiskBehavior()` | Sensitive flows (MFA reset) | `requireLowRiskBehavior(0.5,'mfa-reset')` |

Pair rate limiting with permission gating—do NOT rely solely on quotas for security boundaries.

## Caching Patterns

The caching layer blends application cache + query specialization:

- `cacheResponse()` – Core primitive (controller/user/query headers folded into key)
- `cacheByPermission()` – TTL adaptation admin vs premium vs anonymous
- `cacheQuery()` – Delegates to `QueryCacheService` for repo method memoization
- `cacheFragment()` – Partial page/data island reuse (records hit/miss metrics)
- `cachePaginatedResponse()` – Full pagination result reuse (avoid re‑count + join cost)
- `invalidateResourceCache()` – Post‑mutation invalidation by tags

### Conditional Caching

Use `conditionalCache()` to guard caching behind dynamic constraints:
```php
$data = $this->conditionalCache('metrics:summary', fn() => $this->service->summaries(), [
  'method' => ['GET'],
  'authenticated' => true,
  'min_permission' => 'system.metrics.view',
  'ttl' => 120,
]);
```

### ETag & Last-Modified Workflow
1. Compute resource freshness indicators (hash, updated_at)
2. Call `checkNotModified($lastModified, $etag)` early → return 304 if matched
3. Otherwise build response, set via `withLastModified()` & internal `cached()` helper

## Data Extraction & Normalization

Helpers: `getRequestData()` auto‑parses JSON vs form; `getPutData()` handles PUT/PATCH semantics including raw body parsing when clients tunnel verbs.

Leverage these early—normalize field casing, trim whitespace, then pass the cleaned map to validation & services.

## Error Handling

`handleException()` centralizes mapping:
- `ValidationException` → 422 with detail
- Everything else → generic 500 (logged internally)

Extend this by overriding in specialized controllers if you want domain‑specific mapping (e.g., translate repository not‑found to 404) but prefer one global error middleware for broad concerns.

## ResourceController Pattern (High-Level)

`ResourceController` (extending `BaseController`) layers standardized REST semantics plus toggles:

- Table access toggles: enable/disable bulk operations, write, delete
- Ownership checks & heuristics (avoid exposing multi‑tenant leaks)
- Rate limiting per verb (`read`, `create`, `update`, `delete`, `bulk`)
- Permission fallback hierarchy (operation-specific → resource default → global)
- Field-level filtering (via trait)
- Cache invalidation on mutating operations

Use it for conventional CRUD; graduate to bespoke controllers once behavior diverges substantially (special workflows, orchestration pipelines, streaming responses).

## MetricsController Pattern (Illustrative)

Demonstrates *permission-aware caching* and variable TTLs (admins get fresher data). Combines:
```php
$this->requirePermission('system.metrics.view');
$summary = $this->cacheByPermission('metrics:summary', fn() => $this->collector->aggregate());
return $this->publicCached($this->success($summary), 60);
```

Shows best practice: check permission early, rate limit sensitive endpoints, separate aggregation (service) from presentation.

## Extensibility Guidelines

| Goal | Preferred Strategy |
|------|--------------------|
| Reuse cross-cutting behavior | New focused trait (avoid editing `BaseController`) |
| Swap serialization approach | Provide alternative `Serializer` via DI / config |
| Add custom preconditions | Small domain service injected; controller invokes early |
| Introduce new caching policy | Wrap existing `cacheResponse()` with semantic helper |
| Enhance validation | External validator service; convert its result → `validationError()` |

## Anti-Patterns (Avoid These)

| Smell | Why Harmful | Recommended Fix |
|-------|------------|-----------------|
| Fat controller business logic | Low cohesion, hard to test | Move to service / domain layer |
| Recomputing permissions repeatedly | Wasteful DB/cache churn | Use provided cached methods |
| Manual header() scattering | Hard to maintain / inconsistent | Use response helpers & trait utilities |
| Inline instantiation of infra services | Breaks swap/testability | Rely on DI container injection |
| Expanding lightweight validator endlessly | Scope creep & complexity | Introduce proper validation component |
| Over-caching mutation responses | Stale reads, coherence bugs | Invalidate tags or prefer read-path caching |
| Mixing serialization group logic inline | Duplication + drift | Centralize group decisions near response call |

## Performance Considerations

- Cached user context prevents N identical permission lookups per request.
- Adaptive rate limiting deflects abusive/suspicious patterns early.
- Fragment caching lets you reuse expensive sub-components without whole page coupling.
- Field-level permissions cost O(rows × sensitive_fields); pair with pagination & selective enablement.
  - If high cardinality + many sensitive fields → consider pre-computed filtered projections instead.
- Use `checkNotModified()` early to short‑circuit serialization & downstream service calls for unchanged resources.

## Observability Hooks (Forward-Looking)

Current: Cache metrics via `trackCachePerformance()` (ZSET) + error logging inside `handleException()`.

Planned (see roadmap docs):
- Structured controller execution spans (trace correlation)
- Permission evaluation timing export
- Rate limiter decision metrics (per action)

## Testing Controllers

- Favor calling controller methods with a synthetic `Request` injected (container can build it).
- Mock repositories/services; leave base trait behavior intact to surface integration regressions.
- For caching-sensitive endpoints: prime cache → second invocation asserts reduced path (custom instrumentation or timing threshold).
- For permission flows: seed a `RequestUserContext` fixture with roles/permissions rather than bypassing traits.

## Roadmap & Evolution

| Area | Direction |
|------|-----------|
| Validation | Optional adapter to richer rule engine (no bloat in core) |
| Caching | Tag invalidation batching + warmup orchestrator leveraging provider tags |
| Permission Context | Policy-driven field projections (pre-filter at query time) |
| Rate Limiting | Quota introspection endpoint + sliding window implementation |
| Error Handling | Central exception middleware → slimmer controller concern |

## Summary

Controllers in Glueful are deliberately small: gather intent → enforce constraints → delegate → format → cache. The provided traits give 80% of typical API surface without forcing frameworks like form validators, ORMs, or policy engines prematurely. Extend via composition, not inheritance depth; keep side-effects isolated; and push evolving complexity downward into stable services.
