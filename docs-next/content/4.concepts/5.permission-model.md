# Permission Model

Glueful’s permission system layers a lightweight in‑process Gate (voters + policies) over an optional pluggable provider (RBAC or external ACL service). It emphasizes: deterministic ordering, composability, multi‑tenant safety, low allocation per check, and transparent caching.

## At a Glance

```
Controller / Middleware
   └─ RequestUserContext caches identity + permission results
		└─ PermissionManager::can(userUuid, permission, resource, context)
			  ├─ (mode=replace, provider active) → Provider.can()
			  ├─ (mode=combine) Provider.can() => initial vote (grant/abstain)
			  └─ Gate.decide(identity, permission, resource, Context)
					 (Ordered voters: SuperRole → Policy → Role → Scope → Ownership → Custom)
							   ↓ strategy aggregation (affirmative | unanimous | consensus)
								   → Vote::GRANT / Vote::DENY
```

Provider modes:
- replace: External/provider result exclusively decides.
- combine: Provider contributes an initial vote; core voters still run (short‑circuit rules apply).
- (implicit) gate-only: No provider registered.

## Terminology

| Term | Meaning |
|------|---------|
| Gate | In‑process decision orchestrator that aggregates voter results via a strategy. |
| Voter | Implements tri-state decision (GRANT / DENY / ABSTAIN) with a priority (lower = earlier). |
| Policy | Resource‑specific class whose methods map to abilities (e.g. `update`, `delete`). Accessed via PolicyVoter. |
| Provider | External or extension permission backend (e.g., advanced RBAC, SaaS ACL). |
| PermissionManager | Facade coordinating provider mode vs Gate, building context identity. |
| Context (`Permissions\Context`) | Immutable metadata: tenantId, route params, JWT claims, extra values. |
| Vote Strategy | Aggregation style: affirmative, unanimous, consensus. |
| RequestUserContext | Request‑scoped cache (roles, raw permissions, previously computed checks). |

## Core Components

| Component | Responsibility | Key Points |
|-----------|----------------|-----------|
| `PermissionManager` | Entry point for checks | Modes (replace/combine/gate-only), provider decide hook, builds `UserIdentity` + `Context`. |
| `Gate` | Runs voters & aggregates | Priority sort, strategy logic, optional provider initial vote. |
| `VoterInterface` | Contract for voters | `supports()`, `vote()`, `priority()` (stable ordering). |
| Built‑in Voters | Security heuristics | SuperRole, Policy, Role, Scope, Ownership (in that canonical order). |
| `PolicyRegistry` | Maps resource slug / class → policy instance | Looked up by PolicyVoter using `extra.resource_slug` or class name. |
| `PermissionCache` | Multi-layer cache | Memory + distributed TTL tiers (user permissions, checks, provider data). |
| `RequestUserContext` | Request-level performance layer | Reuses identity data, caches individual check results, does pre‑filters before full Gate. |

## Evaluation Flow

1. Caller (controller trait, middleware, domain service) invokes `PermissionManager::can($userUuid, $perm, $resource, $ctxArray)`.
2. Provider branch:
   - `replace`: Provider directly returns boolean (exception → wraps in PermissionException).
   - `combine`: Provider returns boolean → translated into initial vote (GRANT or ABSTAIN). Deny from provider is treated as ABSTAIN to avoid unilateral provider denial unless configured otherwise.
3. Identity assembly: Roles & raw permissions drawn from `RequestUserContext` when available (ensures correctness + fewer queries).
4. Gate Context built (`Context` object) packing tenant id, JWT claims, route params, extra metadata (e.g. `resource_slug`, `ownerId`).
5. Voter loop in ascending `priority()`:
   1. SuperRoleVoter (immediate grant if user has configured super role)
   2. PolicyVoter (resource policy method → tri-state)
   3. RoleVoter (role → permission or wildcard mapping)
   4. ScopeVoter (JWT/OAuth scope alignment)
   5. OwnershipVoter (owner heuristics via extra/identity)
   6. Custom Voters (any additional registered with their own priorities)
6. Strategy aggregation (see below) returns final GRANT/DENY.
7. Caller interprets result: GRANT → proceed, DENY → 403 / business fallback.

### Strategy Semantics

| Strategy | Rule |
|----------|------|
| affirmative (default) | Return GRANT on first grant if no prior deny; any deny (unless `allow_deny_override=true`) ends with DENY. |
| unanimous | All non-abstain votes must be GRANT; else DENY. Requires at least one GRANT. |
| consensus | Grants > Denies ⇒ GRANT; ties or more denies ⇒ DENY. |

`allow_deny_override=false` (default) yields “hard denials”: an early DENY locks the decision unless override is enabled.

### Provider Combine Mode Edge Cases
Provider exceptions degrade to ABSTAIN (resilience). Provider GRANT still subject to hard deny if a later voter DENIES and overrides are not allowed.

## Context & Identity Construction

`UserIdentity(uuid, roles, scopes, attributes)` is intentionally slim. Roles may be authoritative (role mapping) or advisory (custom voters). Scopes reflect OAuth tokens; attributes may hold pre-fetched permission arrays or domain tags.

`Context` data sources:
- tenantId: Derived from route, header, or explicit parameter.
- routeParams: Router parameter bag.
- jwtClaims: Already parsed claims (no re‑decode inside Gate).
- extra: Flexible map (e.g., `resource_slug`, `ownerId`, feature flags, correlation IDs).

Guideline: treat `Context` as immutable — build new for new checks; do not mutate in voters (side‑effects complicate caching and reasoning).

## Built-in Voters

| Voter | Priority | Purpose | Notes |
|-------|----------|---------|-------|
| SuperRoleVoter | 0 | Fast path super admin grant | Configured `super_roles` list. |
| PolicyVoter | 5 | Resource policy method dispatch | Maps permission tail → method (e.g. `post.update` → `update`). |
| RoleVoter | 10 | Role → permission / wildcard mapping | Supports `*` and prefix wildcards like `post.*`. |
| ScopeVoter | 20 | Token scope alignment | Splits space-delimited scope claim; direct equality. |
| OwnershipVoter | 30 | Owner heuristic | Checks identity vs resource/extra owner markers. |
| Custom | >30 (recommended ≥40) | Extension-specific logic | Provide fine-grained or contextual rules. |

Custom voters should return ABSTAIN unless they have enough information to confidently GRANT or DENY. Keep them side‑effect free.

## Policies

Policy methods allow consolidating resource-specific rules (e.g., post visibility + business constraints). Key mapping: last segment of permission string after final `.` becomes the ability (unless no dot). Method returns:
- true → GRANT
- false → DENY
- null → ABSTAIN (allows later voters to decide)

Use `extra.resource_slug` or the resource class name for registry lookup. Maintain stable slugs for forwards compatibility.

## Caching Layers

| Layer | Scope | Contents | Invalidation |
|-------|-------|----------|-------------|
| RequestUserContext memory | Request | Raw user permissions, roles, previous decisions | Discard end of request. |
| PermissionCache memory | Process | Recently checked permissions & user permissions | TTL or explicit invalidation hooks (roadmap). |
| PermissionCache distributed | Shared (Redis etc.) | User permission sets, provider data, decision results | Tag/version bump (future), TTL expiration. |

Typical flow: decision not in RequestUserContext → check PermissionCache decision bucket → evaluate Gate → store in both memory layers → optional distributed layer.

Performance note: Avoid caching DENY results with very short TTLs if user privileges are likely to change soon (role upgrades). Consider TTL skewing (roadmap) based on result type.

## Naming Conventions

Glueful encourages hierarchical dot notation: `domain.resource.action[.scope]` while keeping tokens meaningful.

Examples:
- `system.metrics.view`
- `posts.update`
- `tenant.user.invite`
- `report.generate.monthly`

Wildcard semantics:
- `posts.*` matches any `posts.X` action.
- `*` (within a role map) grants everything.

Keep actions verbs (view, update, delete, list, invite, generate) and avoid mixing noun forms (`view` not `viewer`).

## Field-Level & Resource-Level Integration

`FieldLevelPermissionsTrait` calls underlying `can()` per field group, enabling redaction lists. Ownership checks feed `extra.ownerId` for OwnershipVoter to consider. Resource controllers feed route params & request attributes into `Context` construction ensuring consistent ownership semantics.

## Extension & Customization

Ways to extend:
1. Register additional voters (service provider → fetch Gate → `registerVoter()`).
2. Provide a custom provider implementing `PermissionProviderInterface` and set mode (`provider_mode`) to `replace` or `combine`.
3. Add policies via config `permissions.policies` mapping slug → policy class.
4. Implement dynamic feature gating voter (e.g. FeatureFlagVoter) using `extra` context.
5. Multi-tenant enforcement voter using `tenantId` guard (deny cross-tenant leakage early).

### Provider Mode Selection
| Scenario | Mode |
|----------|------|
| External centralized RBAC/ABAC service authoritative | replace |
| Gradual migration from legacy provider to Gate | combine |
| Pure in‑process permissions | gate-only |

## Performance & Observability

Instrumentation points:
- PermissionManager wraps provider & gate decisions with timing (debug mode collects duration_ms).
- RequestUserContext optionally logs cache stats in debug (`getCacheStats()`).
- Potential future metric counters: decision latency histogram, cache hit ratio, deny/grant distribution, voter evaluation timing.

Hot path micro-optimizations present:
- Priority-sorted array (usort once per registration) → linear scan.
- Early short-circuit on hard deny or first grant (affirmative). Saves later voter allocations.
- Lazy Gate instantiation only if needed (PermissionManager & RequestUserContext fallback path).

## Anti-Patterns

| Anti-Pattern | Why Problematic | Preferred Approach |
|--------------|-----------------|--------------------|
| Mutating Context inside a voter | Breaks reasoning & caching invariants | Build enriched context before `decide()` call |
| Overloading a single voter with many unrelated concerns | Hard to test / reorder | Split into focused voters with separate priorities |
| Treating ABSTAIN as DENY in business logic | Eliminates composability | Only Gate aggregates; callers use GRANT vs not GRANT |
| Performing DB queries in low-priority voters for common cases | Increases latency | Put cheap deterministic voters first; defer heavy I/O |
| Caching sensitive DENY decisions indefinitely | Stale privilege blocking | Use TTL & explicit invalidation strategy |

## RBAC Extension Boundary

Documentation may reference an “RBAC extension”. That extension can supply:
- Provider implementation (advanced inheritance, group resolution, external sync)
- Additional voters (hierarchical department mapping, feature toggles)
- Migration tooling (dump/export permission graphs)

Core stays minimal: Gate, base voters, policy & context abstractions. Everything else is optional layering.

## Roadmap

| Area | Planned Enhancements |
|------|----------------------|
| Observability | Per-voter timing, structured decision trace export |
| Invalidation | Event-driven cache bust (role change, policy deployment) |
| Dynamic Scopes | Runtime scope alias resolution with caching |

## Practical Usage Examples

Fast path in controller:
```php
if (!$this->can('posts.update')) {
	return $this->forbidden();
}
```

Explicit resource + owner context:
```php
$ok = app(PermissionManager::class)->can(
	$userUuid,
	'posts.update',
	$post, // resource instance
	[
		'tenant_id' => $post->tenant_id,
		'extra' => [ 'ownerId' => $post->author_uuid, 'resource_slug' => 'post' ]
	]
);
```

Custom voter registration in a provider:
```php
public function boot(ContainerInterface $c): void
{
	$gate = $c->get(Gate::class);
	$gate->registerVoter(new FeatureFlagVoter($c->get(FeatureFlagService::class)));
}
```
