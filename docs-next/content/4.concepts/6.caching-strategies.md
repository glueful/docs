# Caching Strategies

Glueful employs layered caching to reduce latency, protect backing stores, and stabilize throughput under load. The system balances correctness with performance by scoping caches, tagging for invalidation, and composing HTTP semantics (ETag / Last‑Modified) with internal data caches.

## Why Multiple Layers?

Different data lifetimes and access patterns demand distinct caching horizons:

| Layer | Scope | Primary Goal | Typical TTL | Eviction Driver |
|-------|-------|-------------|-------------|-----------------|
| Request memory (arrays) | Single request | Remove repeated permission/user lookups | Life of request | Automatic (end of request) |
| Process memory (PermissionCache memory, small static sets) | Worker process | Fast hot path decisions | Minutes–Hour | TTL / deploy recycle |
| Distributed cache (CacheStore) | All workers | Shared data/query/results reuse | Minutes–Hours | TTL / explicit tag invalidation |
| Edge / CDN | Globally distributed | Latency + bandwidth reduction | Seconds–Minutes (HTML), Hours (static) | Manual purge / tag / TTL |

Objective: escalate outward only when necessary. Avoid populating distant caches with unstable data.

## Core Building Blocks

| Component | Purpose | Notes |
|-----------|---------|-------|
| `CacheStore` | Unified PSR-16 + advanced features (tags, patterns, sets) | Driver-agnostic (Redis/Memcached/File) |
| `ResponseCachingTrait` | Controller-level response/query/permission-aware caching helpers | Automatic key composition & ETag aids |
| `QueryCacheService` | Intelligent SQL result caching + table tag extraction | SELECT-only, table parsing for invalidation |
| `PermissionCache` | Multi-layer permission & decision caching | Distinct TTL buckets (permissions vs checks) |
| `EdgeCacheService` | CDN provider abstraction & purge operations | Pluggable via adapters (extension system) |
| `RequestUserContext` | Request-scoped permission & identity memoization | Resets each request; no cross-request bleed |

## Response Caching (Controller Level)

`ResponseCachingTrait::cacheResponse()` composes a key from:
- Controller FQCN
- Logical key hint
- Hash of: query parameters, user UUID (or null), Accept & Accept-Language headers

This ensures content negotiation and personalization do not collide. User-specific tags (`user:<uuid>`) enable targeted invalidation (e.g., user profile update).

### Permission-Aware TTL Adaptation
`cacheByPermission()` changes TTL based on user category (admin / premium / regular / anonymous). Rationale: privileged users require fresher data while anonymous traffic can benefit from longer caching to absorb spikes.

### Paginated Collections
`cachePaginatedResponse()` wraps pagination parameters; tags include `pagination` and `repository:<name>` for coarse invalidation after bulk import or schema migration.

### Conditional Responses
`cachedResponse()` generates deterministic ETags (md5 of serialized payload) & sets `Last-Modified`, returning `304 Not Modified` if the client’s `If-None-Match` matches. This leverages browser + CDN revalidation reducing payload egress.

## Query / Data Caching

`QueryCacheService` focuses on idempotent SELECT queries:
- Rejects non-SELECT or locking (`FOR UPDATE`) queries.
- Skips excluded patterns & tables (config‑driven — future config file addition may expose toggles).
- Hashes (SQL + params) → key; attaches tags: `query_cache:all` plus `query_cache:table:<table>` for each table parsed.
- Supports attribute‑based method caching via `CacheResult` on repository methods with custom TTL & tag injection.

Invalidate specific table caches using `invalidateTable('users')` → purges tags for that table and global set.

### Table Extraction Heuristics
Simple parser enumerates identifiers after `FROM`, `JOIN`, etc. Complex CTE / subquery patterns should be validated; fall back to manual invalidation or attribute tagging for complex SQL.

## Permission & Auth Caching

See [Permission Model](./5.permission-model.md#caching-layers). Summary:
- RequestUserContext: per-request decision memoization (fast repeat `can()` calls inside one controller action).
- PermissionCache: in-memory + distributed TTL tiers for (a) raw user permissions and (b) individual check results.
- Adaptive TTL potential (roadmap) e.g., short TTL for DENY to reflect potential privilege elevation.

## Edge / CDN Caching

`EdgeCacheService` integrates with a CDN adapter resolved via extensions. Capabilities:
- Header generation (cache-control, surrogate keys in future) per route.
- Purge operations: URL, Tag, All.
- Tag purge allows aligning CDN invalidation with internal tag sets (mapping internal `repository:users` to CDN tag `users`).

Edge caching is most effective for:
- High read traffic public endpoints (landing JSON, marketing pages, versioned docs)
- Static assets & media transformations (once image pipeline is integrated with variant caching)

Avoid caching personalized or rapidly mutating resources at the edge unless you implement key partitioning (user segments) or use short TTL + revalidation.

## Tagging & Invalidation Strategy

Tag design guidelines:
| Tag Prefix | Intent |
|------------|--------|
| `user:<uuid>` | Invalidate items tied to a single user (profile, dashboards) |
| `repository:<name>` | Invalidate all cached repository results (CRUD churn) |
| `query_cache:table:<table>` | Purge SQL-derived caches for specific table |
| `pagination` | Bulk invalidation of paginated lists after mass update |
| `admin_cache` / `premium_cache` | Segment-specific caches for tiered users |

Workflow Example (User Update):
1. Persist user changes.
2. Invalidate `user:<uuid>` and maybe `repository:users`.
3. Optional: trigger CDN tag purge if user profile has public edge‑cached variant.

### When to Use Key vs Tag Deletion
| Situation | Approach |
|-----------|----------|
| Singular known stale item | Direct key delete |
| Resource state changed affecting many derived keys | Tag invalidation |
| Structural change (schema/migration deploy) | Pattern or global flush (deploy hook) |

## HTTP Conditional Requests

Leverage both application ETags (`cachedResponse`) and CDN revalidation. Combine with short `max-age` + longer `s-maxage` to differentiate browser vs CDN retention. Use `Vary: Accept, Authorization` to segregate representation & auth state.

## Performance Guidelines

| Principle | Rationale | Example |
|-----------|-----------|---------|
| Cache after correctness | Never serve unvalidated stale inconsistent resources | Validate permissions before caching response |
| Avoid double caching | Prevent layered redundancy & wasted memory | Don’t separately cache query result then wrap identical data in another long-lived response cache without need |
| Prefer coarse invalidation over complex dependency graphs | Simpler reasoning & fewer bugs | Tag whole `repository:orders` instead of managing per‑order composite dependencies |
| Shape keys for low collision | Deterministic hashing of high-variance inputs | Include user UUID + Accept-Language in response key |
| Log cache misses in hot paths (debug mode) | Identify under-cached endpoints | Instrument debug counters in future observability pass |

## Anti-Patterns

| Anti-Pattern | Issue | Mitigation |
|--------------|------|-----------|
| Caching permission-denied responses broadly | Leaks access pattern / over-denies | Only cache positive permission-dependent payloads or use short TTL |
| Unbounded tag cardinality (e.g., tag every object id) | Memory explosion, slow invalidation | Use category or shard tags (bucketed by hash) |
| Storing huge serialized aggregates without compression | Memory pressure | Consider domain-level pagination or compression layer |
| Using `*` pattern deletes in hot path | Expensive O(n) scans | Maintain explicit tag lists |
| Coupling business logic to cache driver features | Portability loss | Rely on `CacheStore` abstraction only |

## Observability & Metrics (Roadmap)

Planned counters:
- cache_hit_total / cache_miss_total (per layer)
- decision_latency_histogram (permission checks)
- edge_purge_operations_total
- query_cache_invalidation_total

Tracing integration will add spans around slow cache misses to highlight N+1 or missing prewarming.

## Roadmap

| Area | Future Enhancements |
|------|---------------------|
| Surrogate Keys | Automatic CDN tag alignment with internal tags |
| Stale-While-Revalidate | Serve stale, refresh async for select endpoints |
| Adaptive TTL | Dynamic TTL lowering for volatile entities (recently modified) |
| Batch Key Operations | Pipeline multi-get for query heavy endpoints |
| Compression | Transparent LZ4/Zstd for large serialized datasets |
| Prewarming | Post-deploy warm tasks / spool for top endpoints |

## Practical Examples

### Cached Paginated List
```php
$users = $this->cachePaginatedResponse('UserRepository', page: $page, perPage: 50);
return $this->success($users);
```

### Permission-Aware Cache
```php
$stats = $this->cacheByPermission('dashboard.metrics', function () {
		return $this->metricsService->computeDashboard();
});
```

### Query Cache With Attribute
```php
#[CacheResult(ttl: 900, tags: ['repository:reports'])]
public function latestReports(int $limit = 20): array { /* ... */ }
```

### CDN Purge After Content Update (Console Command)
```php
php glueful cache:purge --tag=repository:posts
```
