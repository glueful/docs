# Request Lifecycle

Understand how Glueful boots, handles a request, and terminates. This concept provides the durable mental model you need to reason about middleware ordering, performance, observability placement, and safe extension points.

## At a Glance

```
Process start (FPM / Server)            (once)
	└─ Framework boot (providers register, config loaded, container built)
								↓ per-request
Inbound HTTP Request
	└─ Request hydration (globals → Symfony Request)
	└─ Early guard middleware (lockdown / allow_ip / security headers)
	└─ Metrics start + tracing span open (if enabled)
	└─ Routing match (path → handler metadata)
	└─ Auth middleware (credential parsing / user resolution)
	└─ Auth → Request attribute propagation (identity claims)
	└─ Gate attribute middleware (collect & evaluate permission / role attributes)
	└─ Cross-cutting middlewares (rate_limit / csrf / caching / idempotency)
	└─ Request logging middleware (wraps controller) 
	└─ Controller instantiation (via container)
	└─ Action method invocation
	└─ Domain services / DB / queue / events
	└─ Response normalization (JSON / stream / file)
	└─ Tail middleware finalization (logging flush, metrics stop, tracing span close)
Outbound HTTP Response
	└─ (Future) Termination events (long‑running worker cleanup) [roadmap]
```

Two distinct phases exist: a process-level boot (amortized across all requests) and the per-request handling path. Correct separation ensures predictable performance and safe caching of static state.

## Goals of the Lifecycle Design

| Goal | Explanation |
|------|-------------|
| Determinism | Boot phase is pure: no network calls, minimal side effects. |
| Extensibility | Service providers expose a place to register additional services and middleware. |
| Observability | Clear choke points (start, after routing, after controller) for timing + logs. |
| Security | Early middleware layer for lockdown, auth, and permission evaluation. |
| Performance | Avoid repeated container rebuild; keep per-request allocations narrow. |

## Phases in Detail

### 1. Process Boot (One-Time)
Loaded when the runtime (PHP-FPM worker, CLI dev server, or future long-running worker) first includes the framework entry script.

Responsibilities:
1. Load environment variables (.env or server provided)
2. Merge configuration arrays (app, database, cache, permissions, etc.) into a config repository
3. Register core + extension service providers; each provider adds definitions to the container
4. Build/populate dependency injection container (definitions compiled / cached where possible)
5. Register console commands (for CLI contexts) and routing tables

Avoid heavy operations (network calls, migrations) in this phase—defer to dedicated commands.

### 2. Request Hydration
Each inbound HTTP request is converted into a `Symfony\Component\HttpFoundation\Request` instance (see container binding `'request'`). Route candidate matching requires only immutable route metadata (method, path, variables).

### 3. Early Middleware Layer
Executed before route resolution dependent middlewares. Typical responsibilities:
- Global lockdown / maintenance checks
- Basic metrics start timestamp capture
- Request ID / correlation ID generation
- Parsing auth headers (JWT extraction) but deferring heavy user lookups until necessary

### 4. Routing Match
Static route table match yields handler metadata: controller class, method, declared attributes. Path / query params are inserted into request attributes (feeds permission Context routeParams).

### 5. Attribute & Route Middleware Chain
Middleware run in declared order (outer → inner). Recommended ordering pattern:
1. Guard & access filters (lockdown, allow_ip, security_headers)
2. Metrics / tracing starters (lightweight timestamp + optional span creation)
3. Auth (credential parsing & user identity resolution)
4. Auth-to-request propagation (inject identity for downstream consumers)
5. Gate attribute middleware (collects `#[RequiresPermission]` / `#[RequiresRole]`, executes voter pipeline)
6. Cross-cutting protections (rate_limit, csrf, idempotency, caching decorators)
7. Request logging wrapper (captures full latency and status)
8. Domain-specific middlewares (localization, experiments)
9. Tail observability finalizers (metrics stop, span close, structured log flush)

### 6. Controller Instantiation
The container instantiates the controller. Dependencies (services, repositories) are autowired—constructor side effects should be minimal; heavy setup belongs in lazy services.

### 7. Action Execution
The method is invoked with route parameters and (optionally) the Request object. Domain logic delegates quickly to services. Any synchronous DB / cache / queue operations occur here.

### 8. Response Construction
Return value normalized:
- Array / DTO → JSON
- Stream / file handles → streamed response with headers
- Already-built Response objects passed through

### 9. Post-Response Hooks
### 9. Tail Middleware Finalization
Structured log flush (status, latency, correlation ID) occurs in the logging middleware’s finally block. Metrics middleware records counters / histograms at stop time; tracing middleware (roadmap) closes spans here. No separate hook system yet—tail responsibilities are consolidated in middleware.

### 10. Termination (Future)
In current short-lived PHP-FPM execution each request ends with process cleanup. A future long-running worker model will introduce explicit termination events for graceful resource disposal (pool drains, span exporters, buffered queue flush).

## Middleware Ordering Principles

| Order Zone | Purpose | Examples |
|------------|---------|----------|
| Early (pre-auth) | Fast rejection / universal metadata | Lockdown, request ID, metrics start |
| Auth & Security | Establish identity & permissions | Auth attribute propagation, Gate attribute middleware |
| Cross-Cutting | Performance & protection | Rate limiting, idempotency, caching wrappers |
| Domain-Specific | Business concerns | Localization, A/B experiments |
| Observability Tail | Finalize spans & logs | Metrics finalize, log flush |

Design rule: earlier middleware must be cheap; expensive work (DB, external calls) is deferred until after authorization to avoid waste on rejected requests.

## Context Propagation
The `Permissions\Context` captures: route params, tenant ID, JWT claims, and optional extra metadata. It is created just-in-time before permission checks so earlier cheap rejections (lockdown / IP) avoid building unnecessary context. Voters & policies receive the same immutable context instance—avoid mutating it downstream.

## Extension Points
## Extension Points

| Extension Point | When | Contract |
|-----------------|------|----------|
| Service Provider | Boot | Register services, config merges, middleware classes |
| Middleware | Pre/Post controller | `handle(Request, next)` signature; stateless preferred |
| Policies | Permission evaluation | Implement `PolicyInterface` methods return bool/ null|
| Voters | Permission pipeline | Implement `VoterInterface` returning Vote constants |
| Controller Attributes | Before controller | Declarative auth / caching intentions (custom attributes + matching middleware) |
| Post-response events (future) | After response | Planned termination / finalization dispatcher (roadmap) |

## Built-in Middleware Aliases

| Alias | Class | Phase Category | Purpose |
|-------|-------|----------------|---------|
| lockdown | `Routing\Middleware\LockdownMiddleware` | Guard | Emergency maintenance / deny strategy |
| allow_ip | `Routing\Middleware\AllowIpMiddleware` | Guard | IP allowlist gating |
| security_headers | `Routing\Middleware\SecurityHeadersMiddleware` | Guard | Standard security headers injection |
| metrics | `Routing\Middleware\MetricsMiddleware` | Observability (early & tail) | Start/stop timing, counters (roadmap extended) |
| tracing | `Routing\Middleware\TracingMiddleware` | Observability | Span open/close (currently no-op if tracer noop) |
| auth | `Routing\Middleware\AuthMiddleware` | Auth | Credential parsing & user lookup |
| auth_to_request | `Permissions\Middleware\AuthToRequestAttributesMiddleware` | Auth | Propagate identity into request attributes/context |
| gate_permissions | `Permissions\Middleware\GateAttributeMiddleware` | AuthZ | Enforce `RequiresPermission` / `RequiresRole` attributes |
| rate_limit | `Routing\Middleware\RateLimiterMiddleware` | Protection | Throttle excessive usage |
| csrf | `Routing\Middleware\CSRFMiddleware` | Protection | CSRF token validation |
| admin | `Routing\Middleware\AdminPermissionMiddleware` | AuthZ | Shortcut admin privilege check |
| request_logging | `Routing\Middleware\RequestResponseLoggingMiddleware` | Observability (wrapper) | Structured request/response log with latency |

Ordering within categories can shift, but guard middlewares should remain before expensive work; logging wraps core execution to measure total latency; tail responsibilities (metrics stop, span close) belong to the same instrumentation middlewares that started measurement.

## Permission Evaluation Pipeline

When `gate_permissions` middleware runs it orchestrates the Gate’s voter sequence. Default voter order:
1. SuperRoleVoter (immediate grant if super role present)
2. PolicyVoter (resource-specific policy methods)
3. RoleVoter (configured role → permission mapping)
4. ScopeVoter (scope-based permission semantics)
5. OwnershipVoter (resource ownership heuristics)

Strategy (default: affirmative) decides when to short-circuit. `allow_deny_override` controls whether later grants can override an earlier deny. Policies return tri-state (grant/deny/abstain) enabling composition without false negatives.

## Error Propagation & Handling
Exceptions bubble up; a centralized error handler classifies and maps to HTTP responses (JSON problem format). Fail-fast principle: configuration or container errors should surface at boot, not first request.

## Observability Placement
## Observability Placement
- Metrics middleware starts timing at earliest safe point (post basic guards, pre auth) to exclude blocked IP/lockdown trivial rejects if desired (configurable strategy roadmap).
- User & route identifiers are appended after routing + auth (avoid log noise on unmatched/unauthenticated rejects).
- Logging middleware wraps controller to guarantee latency measurement even on exceptions.
- Tracing middleware (roadmap) opens a root span after routing, creates nested spans for controller and DB operations, then closes in tail.
- Future configuration will allow selective exclusion of static asset routes from metrics/logging.

## Performance Considerations
| Concern | Mitigation |
|---------|------------|
| Container build cost | Cache compiled definitions (roadmap) |
| Repeated config parsing | Introduce `config:cache` (roadmap) |
| Cold start latency | Keep boot pure & fast; lazy heavy clients |
| Memory bloat | Use scoped services for large objects (avoid singletons unless safe) |
| Unnecessary DB on 401/403 | Defer expensive loads until after permission checks pass |

## Anti-Patterns
- Performing outbound HTTP calls during service provider registration (non-deterministic boot)
- Mutating global config arrays mid-request (breaks determinism & caching)
- Doing heavy auth user hydration *before* basic permission rejection (wasteful)
- Capturing request-specific state inside singletons (leaks across requests in long-lived workers)
- Swallowing exceptions in middleware without logging (observability blind spot)
