# Service Providers & Bootstrapping

Service Providers are the modular units that publish service definitions, aliases, and tags into the Glueful container during the bootstrap phase. They enable a layered assembly model where core framework capabilities, optional subsystems, and third‑party extensions contribute services without tight coupling.

This concept explains: lifecycle phases, provider ordering, the tagging & aggregation pass, extension discovery, lazy warmup metadata, controller & command registration, and how providers interact with container compilation.

## Goals

| Goal | Why It Matters |
| ---- | -------------- |
| Deterministic ordering | Predictable overrides & tag priority evaluation |
| Declarative contribution | Providers return pure definition arrays; no imperative side effects required |
| Extension isolation | Third‑party packages can add or override services safely |
| Tag-first aggregation | Pipelines & collections formed uniformly (commands, warmups, etc.) |
| Compilation readiness | Structure encourages compiler-friendly (autowire/value/alias) definitions |
| Test override ergonomics | Minimal differences between prod & test resolution path |

## High-Level Flow

```
ContainerFactory::create(prod?)
	-> instantiate TagCollector
	-> build ordered provider class list
	-> foreach provider: collect defs(), record tag() calls
	-> load extension definitions (typed defs() or DSL services())
	-> synthesize TaggedIteratorDefinition for each collected tag
	-> inject ParamBag (env, etc.)
	-> build runtime Container ($definitions)
	-> (prod) attempt load precompiled OR compile definitions -> CompiledContainer
	-> return container implementation
```

## Provider Anatomy

Providers extend `BaseServiceProvider` and must implement:

```php
abstract class BaseServiceProvider {
	abstract public function defs(): array; // id => (DefinitionInterface|callable|mixed)
	protected function autowire(string $fqcn, bool $shared = true): AutowireDefinition { /* ... */ }
	protected function tag(string $serviceId, string $tagName, int $priority = 0): void { /* ... */ }
	protected function alias(string $aliasId, string $targetId): AliasDefinition { /* ... */ }
}
```

Providers are purely declarative: return definitions; use helper methods to register tags & aliases. No direct container mutation occurs here—construction happens later.

| Provider | Responsibility Highlights |
| -------- | ------------------------- |

| `StorageProvider` | Storage backends & file abstractions |
| `RequestProvider` | HTTP/Symfony Request + PSR-7 ServerRequest + request/session/environment contexts |
| `ValidationProvider` | Validation services & rules (from validation subsystem) |
| `SerializerProvider` | Serialization / formatting services |
| `EventProvider` | Event bus / dispatcher (tagging listeners) |
| `QueueProvider` | Queue workers, scheduler, autoscaler |
| `LockProvider` | Distributed / in-memory lock managers |
| `FileProvider` | File system interactions |
| `SpaProvider` | SPA asset/server helpers |
| `HttpPsr15Provider` | PSR-15 handler/middleware bridge |
| `VarDumperProvider` | Debugging dumps integration |
| `ImageProvider` | Image processing services |

Order matters when one provider depends on another's tags or definitions (e.g., `LazyProvider` reads tags aggregated so far). Only minimal implicit assumptions should exist; otherwise document them.

## Tag Lifecycle

1. During each provider's `defs()` execution, calls to `$this->tag(id, name, priority)` push entries into `TagCollector`.
2. After all providers and extensions load, `ContainerFactory` converts each tag bucket into a `TaggedIteratorDefinition` keyed by the tag name.
3. These collections are shared (singleton arrays) and stable in ordering (priority desc, then insertion order for ties once sorted).

### Common Tags

| Tag | Meaning |
| --- | ------- |
| `console.commands` | All console command classes to register with CLI application |
| `lazy.background` | Heavy services safe to warm up asynchronously after boot |
| `lazy.request_time` | Services worth warming early in first-request path |
| `cache.pool` | Cache pool implementations or stores |
| `http.request` | Request object convenience referencing (from RequestProvider) |

Extensions may introduce additional semantic tags; naming should be namespaced or clear to avoid collisions.

## Example: ConsoleProvider

`ConsoleProvider` enumerates command classes, autowires each, and tags them:

```php
foreach ($commands as $class) {
	$defs[$class] = $this->autowire($class);
	$this->tag($class, 'console.commands');
}
```

Later the CLI application resolves the `console.commands` tagged iterator to register all commands dynamically.

## Example: LazyProvider

`LazyProvider` inspects previously collected tag entries to build *ID lists* without instantiating the services:

```php
$background = collectIds($all['lazy.background']);
$defs['lazy.background.ids'] = new ValueDefinition('lazy.background.ids', $background);
```

Then it exposes a `LazyInitializer` factory that can orchestrate background warmup passes. This demonstrates cross-provider collaboration via tags without tight coupling.

## Extension Discovery & Loading

`ProviderLocator::all()` returns class names discovered from enabled extensions. Each is processed:

1. If class has static `defs()` → array merged directly + optional `tags()` mapping applied.
2. Else if class has static `services()` DSL → parsed by `ServicesLoader` into definitions & tag metadata applied.
3. Errors during load are logged (non-fatal) to avoid breaking core bootstrap.

### Tag Publication by Extensions

* Typed provider: implement `public static function tags(): array` returning `['tag.name' => ['service.id', ['service' => 'svc', 'priority' => 10]]]`.
* DSL: embed `tags` key per service specification.

## Controller & Middleware Registration

* Controllers: Autowired through `ControllerProvider` so route resolution can simply `new ControllerClass(...)` via container.
* Middleware: Core middleware classes autowired in `CoreProvider` plus user-friendly string aliases (e.g., `auth`, `rate_limit`).

## ParamBag Injection Timing

`ParamBag` is inserted after provider execution but before container instantiation so autowired constructor injection via `#[Inject(param: 'env')]` sees a consistent environment value whether or not compilation occurs later.

## Compilation Interplay

Compilation only occurs *after* providers & extensions have supplied the full definition graph. To maximize compile coverage:

| Practice | Benefit |
| -------- | ------- |
| Favor `AutowireDefinition` over heavy `FactoryDefinition` | Compiler can emit static build methods |
| Convert static config to `ValueDefinition` | Eliminates runtime logic, compiles directly |
| Keep factories side-effect free & deterministic | Easier to refactor into autowired classes |
| Avoid container access inside factories unless essential | Reduces hidden dependencies, aids future static analysis |

If unsupported definitions remain, compile gracefully fails and runtime container persists (no breakage—only performance delta).

| Phase | Purpose | Sources |

## Testing & Overrides

Providers are deterministic; tests can:

* Build the normal container via `ContainerFactory::create(false)`.
* Layer overrides using `$container->with(['service.id' => fn() => new FakeService])` without modifying provider code.
* Supply test-only provider definitions by merging arrays before instantiation (custom test harness) if needed.

## Recommended Practices

1. Keep provider `defs()` pure—avoid IO; push variability to factories or configuration services.
2. Tag first, aggregate later. Don’t build arrays manually when a tag + `TaggedIteratorDefinition` suffices.
3. Use semantic tag names that reflect intent (`metrics.collectors`, `queue.workers`).
4. Prefer explicit alias for interface bindings—even if the implementation class name matches—to retain refactor freedom.
5. Document priority meaning in extension READMEs when exposing tagged extension points.
6. Promote factories to dedicated classes as they grow; easier to test and compile.

## Anti‑Patterns

| Anti-Pattern | Issue | Better Approach |
| ------------ | ----- | --------------- |
| Hidden side effects in provider (starting threads, IO) | Non-deterministic boot, hinders compilation | Move to explicit runtime service method or command |
| Large conditional blocks in `defs()` | Hard to read/override | Delegate to small factory classes or config maps |
| Ad-hoc arrays of services built manually | Ordering / duplication bugs | Use tagging + `TaggedIteratorDefinition` |
| Overusing priorities to encode branching logic | Implicit & fragile | Model explicit pipeline or policy class |
| Mutating global state in provider | Pollution, test flakiness | Constrain mutation to service runtime methods |

## Minimal Example Provider

```php
final class SearchProvider extends BaseServiceProvider {
	public function defs(): array {
		$defs = [];
		$defs[SearchClient::class] = $this->autowire(SearchClient::class);
		$defs[SearchIndexManager::class] = $this->autowire(SearchIndexManager::class);
		$this->tag(SearchIndexManager::class, 'lazy.background', 10);
		return $defs;
	}
	// Optionally: public static function tags() { return ['metrics.collectors' => ['search.metrics']]; }
}
```

## Summary

Providers modularize Glueful's bootstrap into composable, inspectable layers. Tagging creates declarative extension seams; deterministic ordering plus clean definition semantics enable a fast path to compilation and future warmup strategies. Keep providers pure and explicit to preserve clarity, testability, and performance.
